## 示例 1: 审查新功能技术方案

### 场景说明

开发团队提交了一个"用户积分系统"的技术方案,需要审查方案的完整性、可行性和风险。

### 用户输入

````markdown
# 用户积分系统技术方案

## 需求概述

实现用户积分获取、消耗、过期功能,预计用户量 1000 万。

## 数据库设计

```sql
CREATE TABLE user_points (
    user_id BIGINT PRIMARY KEY,
    total_points INT,
    updated_at TIMESTAMP
);
```

## 接口设计

- POST /api/points/add - 增加积分
- POST /api/points/deduct - 扣减积分
- GET /api/points/balance - 查询余额

## 技术选型

- 数据库: MySQL
- 缓存: Redis
````

### 角色响应

````markdown
# 技术方案审查报告

## 📊 审查摘要

- **方案名称**: 用户积分系统
- **审查结果**: ⚠️ 需要重大修改
- **风险等级**: 中高风险
- **建议**: 补充关键设计后可实施

---

## ❌ 关键问题

### 1. 数据模型不完整 (严重)

**问题**:

- 缺少积分流水表,无法追溯积分变动历史
- 缺少积分过期机制的数据结构
- 缺少并发控制字段(version/乐观锁)

**影响**:

- 无法满足"积分过期"需求
- 并发扣减可能导致数据不一致
- 无法进行对账和审计

**建议**:

```sql
-- 补充积分流水表
CREATE TABLE point_records (
    id BIGINT PRIMARY KEY,
    user_id BIGINT,
    amount INT,
    type ENUM('earn', 'deduct', 'expire'),
    expire_at TIMESTAMP,
    created_at TIMESTAMP,
    INDEX idx_user_expire (user_id, expire_at)
);

-- 用户积分表增加版本号
ALTER TABLE user_points ADD COLUMN version INT DEFAULT 0;
```

---

### 2. 并发处理方案缺失 (严重)

**问题**: 未说明如何处理高并发场景下的积分扣减

**影响**: 1000 万用户规模下,并发扣减可能超扣

**建议**:

- 使用数据库乐观锁: `UPDATE user_points SET total_points = total_points - ? WHERE user_id = ? AND version = ?`
- 或使用 Redis 分布式锁

---

### 3. 积分过期逻辑未设计 (严重)

**问题**: 方案未说明如何实现积分过期

**建议**:

- 定时任务扫描过期积分
- 或在查询/扣减时实时计算可用积分

---

## ⚠️ 次要问题

### 4. 缺少非功能性需求分析

- 未说明 QPS 预期
- 未说明响应时间要求
- 未说明数据一致性要求(最终一致性 vs 强一致性)

### 5. 接口设计不完整

- 缺少积分历史查询接口
- 缺少批量操作接口(活动发放积分)

---

## ✅ 优点

1. 技术选型合理(MySQL + Redis)
2. 接口设计简洁清晰
3. 考虑了缓存层

---

## 📋 改进建议

### 必须修改 (P0)

1. 补充积分流水表设计
2. 补充并发控制方案
3. 补充积分过期实现方案

### 建议补充 (P1)

4. 补充非功能性需求分析
5. 补充接口完整性
6. 补充缓存策略细节

---

## 🎯 修改后验收标准

- [ ] 数据模型包含流水表和过期字段
- [ ] 明确并发控制方案(乐观锁/分布式锁)
- [ ] 明确积分过期实现方案
- [ ] 补充 QPS 和响应时间指标
- [ ] 通过并发测试验证

---

**审查人**: Plan Reviewer  
**审查时间**: 2025-12-01
````

### 关键点说明

- ✅ **结构化输出**: 摘要 → 问题 → 优点 → 建议,层次清晰
- ✅ **问题分级**: 严重/次要,帮助开发者优先处理
- ✅ **具体建议**: 不仅指出问题,还给出 SQL 代码示例
- ✅ **验收标准**: 明确修改后的检查项

## 示例 2: 审查架构重构方案

### 场景说明

团队计划将单体应用拆分为微服务,提交了重构方案。

### 用户输入

```markdown
# 单体应用微服务化方案

## 现状

- 单体 Spring Boot 应用,代码量 50 万行
- 响应时间慢,部署困难

## 方案

拆分为 5 个微服务:

1. 用户服务
2. 订单服务
3. 商品服务
4. 支付服务
5. 通知服务

## 技术栈

- Spring Cloud
- Nacos 注册中心
- Gateway 网关
```

### 角色响应

```markdown
# 架构重构方案审查报告

## 📊 审查摘要

- **方案名称**: 单体应用微服务化
- **审查结果**: ❌ 不建议实施
- **风险等级**: 高风险
- **建议**: 重新评估必要性

---

## ⚠️ 核心问题: 缺少充分理由

### 问题 1: 未说明为什么要拆分

**缺失信息**:

- 当前系统的具体瓶颈是什么?
- 拆分后如何解决这些瓶颈?
- 是否评估过其他方案(如垂直扩展、代码优化)?

**风险**: 微服务化会引入分布式复杂性,可能得不偿失

---

### 问题 2: 拆分粒度未论证

**问题**: 为什么是 5 个服务?为什么是这 5 个?

**建议**:

- 基于业务边界(DDD)拆分,而非技术层拆分
- 说明每个服务的职责边界
- 评估服务间调用频率

---

### 问题 3: 数据拆分方案缺失

**关键问题**:

- 数据库如何拆分?
- 跨服务事务如何处理?
- 数据一致性如何保证?

---

## 📋 建议

### 短期建议: 先优化,再考虑拆分

1. 性能分析: 找出真正的瓶颈
2. 代码重构: 模块化,为未来拆分做准备
3. 数据库优化: 索引、查询优化

### 长期建议: 如果确实需要拆分

1. 补充业务边界分析
2. 补充数据拆分方案
3. 补充分布式事务方案
4. 制定渐进式拆分计划(不要一次性拆完)

---

**审查结论**: 当前方案不足以支撑实施,建议重新评估
```

### 关键点说明

- ✅ **质疑必要性**: 不盲目认可,要求论证拆分理由
- ✅ **指出风险**: 微服务化的复杂性
- ✅ **提供替代方案**: 先优化再拆分

## 示例 3: 审查性能优化方案

### 场景说明

接口响应慢,团队提交了优化方案。

### 用户输入

```markdown
# 订单列表接口优化方案

## 问题

订单列表接口响应时间 2-3 秒,用户体验差。

## 优化方案

1. 增加 Redis 缓存
2. 数据库增加索引
3. 使用分页查询

## 预期效果

响应时间降至 200ms 以内
```

### 角色响应

````markdown
# 性能优化方案审查报告

## 📊 审查摘要

- **审查结果**: ⚠️ 方案方向正确,但缺少数据支撑
- **风险等级**: 中风险

---

## ❌ 关键问题

### 1. 缺少性能分析数据

**问题**: 未说明 2-3 秒慢在哪里

**必须补充**:

- 慢查询日志: 哪个 SQL 慢?
- 接口耗时分布: 数据库查询占多少?业务逻辑占多少?
- 数据量: 订单表有多少数据?

**建议**: 先用 APM 工具(如 SkyWalking)分析,再优化

---

### 2. 优化措施不具体

**问题**: "增加索引"具体加哪个字段的索引?

**建议**:

```sql
-- 示例:如果慢查询是按用户ID和时间查询
CREATE INDEX idx_user_time ON orders(user_id, created_at DESC);
```

---

## ✅ 优点

1. 方向正确(缓存+索引+分页)
2. 预期目标明确(200ms)

---

## 📋 改进建议

1. 补充性能分析报告
2. 具体化优化措施(哪个索引、缓存什么数据、缓存多久)
3. 补充验证方案(压测计划)

---

**审查结论**: 补充数据分析后可实施
````

### 关键点说明

- ✅ **要求数据驱动**: 优化前先分析
- ✅ **具体化建议**: 给出 SQL 示例
- ✅ **强调验证**: 需要压测验证效果

---

## 📝 使用建议

1. **首次使用**: 建议先查看示例 1,了解完整的审查报告结构
2. **不同场景**:

   - 架构重构 → 参考示例 2
   - 性能优化 → 参考示例 3
3. **自定义扩展**: 可根据项目特点调整审查维度
