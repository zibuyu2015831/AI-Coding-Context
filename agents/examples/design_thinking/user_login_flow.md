# 示例: 用户登录流程设计 (Design Thinking Walkthrough)

本文档展示了使用**设计思维引导模式**设计"用户登录功能"的完整过程。

---

## 场景背景

**用户需求**: "我需要添加用户登录功能"

**触发**: 用户输入 `@think:standard 添加用户登录功能`

---

## 📊 Step 1: 问题本质 (ProductManager)

### 5 Why 分析

1. **为什么需要用户登录功能?**  
   → 因为系统需要识别不同用户,提供个性化服务。

2. **为什么需要个性化服务?**  
   → 因为不同用户有不同的权限和数据,需要隔离。

3. **为什么需要权限隔离?**  
   → 因为系统包含敏感数据(如订单、支付信息),不能被未授权用户访问。

4. **为什么敏感数据访问控制很重要?**  
   → 因为数据泄露会导致财务损失和信任危机,影响业务生存。

**根本动机**:  
→ **保障数据安全,建立用户信任,支撑业务核心功能**。

---

### 需求摘要

- **核心功能**: 支持用户通过用户名/邮箱 + 密码登录系统
- **业务价值**: 数据安全隔离,建立信任,满足合规要求
- **目标用户**: 所有注册用户(B2C 场景)
- **使用场景**: 首次访问、会话过期后重新登录

---

### 初步成功标准

- [ ] 用户可以使用正确凭证成功登录
- [ ] 错误凭证无法登录,并有明确提示
- [ ] 登录后会话保持 7 天 (可配置)
- [ ] 支持"记住我"功能

---

## 🏗️ Step 2: 方案探索 (ArchitectureAnalyst)

### 方案对比

#### 方案 A: Session-based (传统会话)

**核心思路**: 服务端维护会话状态,通过 Cookie 传递 Session ID

**技术选型**: Express-session + Redis

**优点**:

- 服务端完全掌控会话,易于撤销
- 支持复杂的会话管理 (如单点登录)

**缺点**:

- 需要 Redis 等存储,增加运维成本
- 水平扩展时需要会话共享

**成本评估**: 开发 3 天,需要 Redis 基础设施

---

#### 方案 B: JWT Token (无状态)

**核心思路**: 签发 JWT Token,客户端存储,每次请求携带

**技术选型**: jsonwebtoken + HttpOnly Cookie

**优点**:

- 无状态,易于水平扩展
- 不依赖额外存储,简化架构

**缺点**:

- Token 无法主动撤销 (除非加黑名单)
- Token 泄露风险高于 Session

**成本评估**: 开发 2 天,无额外基础设施

---

### 推荐方案

**选择**: 方案 B (JWT Token)

**理由**:

- 当前系统用户量小 (<10 万),无状态方案足够
- 团队已有 JWT 使用经验,开发速度快
- 避免引入 Redis,降低运维复杂度
- Token 有效期设为 15 分钟 + Refresh Token 7 天,平衡安全与体验

---

### 边界定义

**本次实现**:

- 用户名/邮箱 + 密码登录
- JWT Access Token (15 分钟) + Refresh Token (7 天)
- 登录失败 5 次后锁定账户 15 分钟

**本次不实现**:

- OAuth 第三方登录 (Google/Facebook) → 理由: 非核心需求,V2 功能
- 短信验证码登录 → 理由: 成本高,暂无明确需求
- 多因子认证 (MFA) → 理由: 当前业务敏感度不高

**后续版本考虑**:

- 支持 Google/Facebook OAuth
- 手机号 + 验证码登录

---

## ⚠️ Step 3: 风险与测试 (Architect & QA)

### 技术风险评估

#### 风险 1: JWT Token 泄露导致账户劫持

**描述**: 如果 Token 被 XSS 攻击窃取,攻击者可冒充用户

**影响**: High - 直接导致用户数据泄露

**应对措施**:

- Token 存储在 **HttpOnly Cookie** 中,防止 JavaScript 读取
- 启用 **HTTPS** 强制加密传输
- 设置短有效期 (15 分钟) + Refresh Token 机制
- 实施 Content Security Policy (CSP) 防止 XSS

---

#### 风险 2: 暴力破解密码

**描述**: 攻击者通过自动化工具尝试大量密码组合

**影响**: Medium - 可能导致弱密码账户被攻破

**应对措施**:

- 登录失败 5 次锁定账户 15 分钟
- 实施 Rate Limiting (同一 IP 每分钟最多 10 次尝试)
- 强制密码复杂度要求 (8 位以上,含字母+数字)

---

#### 风险 3: Refresh Token 被盗用

**描述**: 如果 Refresh Token 被窃取,攻击者可长期冒充用户

**影响**: High - 危害比 Access Token 更大

**应对措施**:

- Refresh Token 使用 **Rotating Refresh Token** 模式 (每次刷新换新 Token)
- 检测到异常刷新 (如同一 Token 多次使用) 立即撤销
- 用户可手动撤销所有 Token (退出所有设备)

---

### 测试策略

#### 测试覆盖范围

- **功能测试**: 正常登录、失败登录、Token 刷新、Token 过期
- **性能测试**: 并发 1000 用户登录,响应时间 < 500ms
- **安全测试**: SQL 注入、XSS、CSRF、暴力破解

#### 测试类型分布

- **单元测试**: JWT 生成/验证逻辑、密码哈希验证
- **集成测试**: 登录 API + 数据库联调
- **端到端测试**: 用户从登录页到首页的完整流程

---

### 验收标准 (细化)

#### 功能性标准

- [ ] 用户输入正确用户名+密码,返回 200 OK 和 JWT Token
- [ ] 用户输入错误密码,返回 401 Unauthorized 和错误提示
- [ ] 用户不存在时,返回 404 Not Found (或模糊提示"用户名或密码错误")
- [ ] **边界测试**: 连续 5 次失败后,第 6 次返回 429 Too Many Requests
- [ ] **边界测试**: Access Token 过期后,请求受保护资源返回 401
- [ ] **异常测试**: Refresh Token 过期后,刷新失败并要求重新登录

#### 非功能性标准

- [ ] **性能**: 单次登录响应时间 < 300ms (P99)
- [ ] **安全**: 密码使用 bcrypt 加密存储 (cost=12)
- [ ] **可用性**: 登录失败时,明确提示错误原因 (非技术黑话)

#### 测试数据准备

- 正常数据: 10 个测试用户 (有效凭证)
- 边界数据: 弱密码用户、锁定用户、过期 Token
- 异常数据: SQL 注入字符串、超长密码 (10000 字符)

## ✅ Step 5: 最终决策 (Facilitator)

### 1. 背景与目标

#### 业务价值

**保障数据安全,建立用户信任,支撑业务核心功能**。通过实施可靠的用户认证机制,确保敏感数据只能被授权用户访问,满足合规要求,避免数据泄露风险。

#### 核心需求

- 支持用户名/邮箱 + 密码登录
- 会话保持 (Access Token 15 分钟 + Refresh Token 7 天)
- 防止暴力破解 (失败锁定 + Rate Limiting)
- Token 安全存储 (HttpOnly Cookie)

#### 目标用户与使用场景

- **目标用户**: 所有注册用户 (B2C 场景)
- **使用场景**: 首次访问、会话过期后重新登录、跨设备登录

---

### 2. 技术方案

#### 推荐方案

**方案名称**: JWT Token 无状态认证方案

**核心思路**: 使用 JWT 签发 Access Token (短期) + Refresh Token (长期),通过 HttpOnly Cookie 存储,避免 XSS 攻击

**技术选型**:

- **JWT 库**: jsonwebtoken (Node.js)
- **密码加密**: bcrypt (cost=12)
- **存储方式**: HttpOnly + Secure + SameSite=Strict Cookie
- **传输协议**: HTTPS 强制

**关键设计点**:

- Access Token 有效期 15 分钟,包含用户 ID 和权限信息
- Refresh Token 有效期 7 天,使用 Rotating Token 模式 (每次刷新换新)
- 登录失败 5 次锁定账户 15 分钟
- 实施 Rate Limiting (同一 IP 每分钟 10 次)

#### 备选方案

**方案 A (Session-based)** 未采纳,原因:

- 需要 Redis 基础设施,增加运维成本
- 当前用户量小,无状态方案足够

---

### 3. 实现边界

#### 本次实现

- 用户名/邮箱 + 密码登录
- JWT Access Token (15 分钟) + Refresh Token (7 天)
- 登录失败锁定机制
- HttpOnly Cookie 存储
- HTTPS 强制传输

#### 本次不实现

- **OAuth 第三方登录** (Google/Facebook) → 理由: 非核心需求,V2 功能
- **短信验证码登录** → 理由: 成本高,暂无明确需求
- **多因子认证 (MFA)** → 理由: 当前业务敏感度不高,可后续升级

---

### 4. 风险与应对

| 风险                 | 影响 | 应对措施                                                        |
| -------------------- | ---- | --------------------------------------------------------------- |
| JWT Token 泄露       | High | HttpOnly Cookie + HTTPS + 短有效期 (15 分钟) + Refresh Token    |
| 暴力破解密码         | Med  | 失败锁定 (5 次/15 分钟) + Rate Limiting + 强密码策略            |
| Refresh Token 被盗用 | High | Rotating Refresh Token + 异常检测 + 用户可手动撤销所有 Token    |
| XSS 攻击窃取 Token   | Med  | HttpOnly Cookie (JavaScript 无法读取) + Content Security Policy |
| CSRF 攻击利用 Cookie | Med  | SameSite=Strict + CSRF Token (Double Submit Cookie 模式)        |

---

### 5. 验收标准

#### 功能性标准

- [ ] 用户输入正确凭证成功登录,返回 200 OK 和 JWT Token
- [ ] 错误密码返回 401,明确提示"用户名或密码错误"
- [ ] 用户不存在时,返回统一的模糊提示 (防止用户名枚举)
- [ ] **边界测试**: 连续 5 次失败后账户锁定 15 分钟
- [ ] **边界测试**: Access Token 过期后请求受保护资源返回 401
- [ ] **异常测试**: Refresh Token 过期后刷新失败,要求重新登录
- [ ] **安全测试**: SQL 注入字符串无法绕过验证

#### 非功能性标准

- [ ] **性能**: 登录响应时间 < 300ms (P99)
- [ ] **安全**: 密码使用 bcrypt (cost=12) 加密存储
- [ ] **安全**: Token 通过 HTTPS 传输
- [ ] **可用性**: 登录失败时有明确且用户友好的错误提示

---

### 6. 测试策略

- **单元测试**: JWT 生成/验证逻辑、密码哈希验证、失败计数器逻辑
- **集成测试**: 登录 API + 数据库联调、Token 刷新流程
- **端到端测试**: 用户从登录页输入凭证到成功访问首页的完整流程
- **安全测试**: SQL 注入、XSS、CSRF、暴力破解模拟

---

#### 后续规划

- **V2.5**: 添加手机号 + 验证码登录

## 📝 总结

通过**设计思维引导模式**,我们:

1. ✅ 通过 5 Why 分析,明确了登录功能的**根本业务价值** (数据安全与用户信任)
2. ✅ 对比了 Session 和 JWT 两种方案,**基于项目现状**选择了 JWT
3. ✅ 识别了 3 个主要风险,并给出了**具体可执行的应对措施**
4. ✅ 制定了**明确可测试的验收标准**,包含边界和异常场景
5. ✅ 输出了**结构化的决策方案**,可直接作为实施依据

相比直接编码,设计思维引导帮助我们:

- **避免了盲目跟风** (不是因为 JWT 流行就用,而是基于项目规模和团队能力)
- **提前发现了安全风险** (Token 泄露、暴力破解、Refresh Token 盗用)
- **明确了边界** (不做 OAuth,避免范围蔓延)
- **确保了可测试性** (每个验收标准都可转化为测试用例)

这就是设计思维引导的价值:**想清楚再动手,一次做对**。
