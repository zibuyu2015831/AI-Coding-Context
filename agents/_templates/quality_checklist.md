# 角色质量检查清单

**用途**: 用于角色改造和创建过程中的质量验收  
**版本**: v1.0  
**最后更新**: 2025-11-29

---

## 使用说明

本检查清单用于确保每个角色定义达到质量标准。在提交角色定义前,请逐项检查以下内容。

**检查流程**:

1. **自检** - 角色创建者使用本清单自检
2. **同行评审** - 其他开发者使用本清单评审
3. **最终验收** - 框架作者使用本清单验收

---

## 一、格式检查 ✅

### 1.1 元数据完整性

- [ ] **必需字段齐全**

  - [ ] ID (格式: `类型.英文名称`)
  - [ ] 名称 (中文)
  - [ ] 类型 (runtime/development/language_specific)
  - [ ] 版本 (格式: `vX.Y`)
  - [ ] 创建日期 (格式: `YYYY-MM-DD`)
  - [ ] 更新日期 (格式: `YYYY-MM-DD`)

- [ ] **推荐字段存在**

  - [ ] 来源 (参考来源说明)
  - [ ] 改造状态 (已通用化/待改造)
  - [ ] 语言支持 (通用/特定语言)
  - [ ] 依赖角色列表
  - [ ] 被依赖角色列表

- [ ] **可选字段合理**
  - [ ] 标签列表 (3-5 个相关标签)

### 1.2 章节完整性

- [ ] **必需章节存在**

  - [ ] 📋 角色概述
  - [ ] 🎯 角色设定 (System Prompt)
  - [ ] 💡 输入要求
  - [ ] 📤 输出要求
  - [ ] 📊 评估标准

- [ ] **推荐章节存在**
  - [ ] 📚 参考示例
  - [ ] 🔗 协作角色
  - [ ] 📝 使用说明

### 1.3 格式规范性

- [ ] **Markdown 格式正确**

  - [ ] 标题层级正确 (H1 → H2 → H3)
  - [ ] 列表格式统一
  - [ ] Checkbox 格式正确 (`- [ ]`)
  - [ ] 链接格式正确

- [ ] **Emoji 使用一致**

  - [ ] 章节标题使用规范 emoji
  - [ ] ✅/❌ 标记正确使用

- [ ] **代码块格式**
  - [ ] 代码块标注语言类型
  - [ ] 伪代码/示例代码清晰

## 二、内容检查 📝

### 2.1 角色概述

- [ ] **快速说明信息完整**
  - [ ] 职责 - 一句话清晰描述
  - [ ] 适用场景 - 列举 2-3 个典型场景
  - [ ] 专长领域 - 列举 3-5 个专长
  - [ ] 协作角色 - 指出相关角色

### 2.2 角色设定

- [ ] **身份定义明确**

  - [ ] 使用"你是一位经验丰富的 xxx 专家"模板
  - [ ] 明确专注领域
  - [ ] 列举核心职责(至少 3 项)

- [ ] **行为准则清晰**

  - [ ] "应该做"至少 5 项,具体可执行
  - [ ] "不应该做"至少 3 项,明确禁止行为
  - [ ] 无模糊或歧义表述

- [ ] **输出规范明确**
  - [ ] 输出格式要求具体
  - [ ] 质量标准可验证
  - [ ] 提供格式模板(如适用)

### 2.3 输入输出要求

- [ ] **输入要求明确**

  - [ ] 列举所有必需输入项
  - [ ] 说明每项输入的用途
  - [ ] 区分必需/可选输入

- [ ] **输出要求具体**
  - [ ] 列举所有输出项
  - [ ] 说明每项输出的格式和内容
  - [ ] 输出可独立验证

### 2.4 评估标准

- [ ] **检查项完整**

  - [ ] 至少包含 4 个维度(功能/技术/文档/可维护性)
  - [ ] 每个维度至少 2-3 个检查项
  - [ ] 总计至少 10 个检查项

- [ ] **检查项可验证**
  - [ ] 每项都是具体的、可验证的
  - [ ] 避免主观或模糊的标准
  - [ ] 使用 Checkbox 格式 (`- [ ]`)

### 2.5 协作关系

- [ ] **协作关系明确**
  - [ ] 标注上游角色(如有)
  - [ ] 标注下游角色(如有)
  - [ ] 标注配合角色(如有)
  - [ ] 说明协作方式

## 三、质量检查 ⭐

### 3.1 通用化程度

- [ ] **去语言特定性**

  - [ ] 无特定编程语言的语法(除非是 language_specific 类型)
  - [ ] 无特定框架的 API 调用
  - [ ] 使用通用术语和概念

- [ ] **去技术栈绑定**

  - [ ] 不绑定特定工具或平台
  - [ ] 支持多种技术实现方案
  - [ ] 提供跨技术栈的通用指导

- [ ] **适应性强**
  - [ ] 可应用于不同项目规模
  - [ ] 可应用于不同业务场景
  - [ ] 可根据实际情况调整

### 3.2 清晰性和可理解性

- [ ] **语言表达**

  - [ ] 语言通顺,无语病
  - [ ] 术语使用准确
  - [ ] 避免过度专业化的行话
  - [ ] 逻辑清晰,易于理解

- [ ] **结构组织**
  - [ ] 章节划分合理
  - [ ] 层次结构清晰
  - [ ] 信息组织有序
  - [ ] 重点突出

### 3.3 实用性和可操作性

- [ ] **可直接使用**

  - [ ] 无需大量修改即可使用
  - [ ] 提供足够的上下文信息
  - [ ] 示例真实有效

- [ ] **指导性强**
  - [ ] 提供明确的行动指南
  - [ ] 给出具体的操作步骤
  - [ ] 包含最佳实践建议

### 3.4 Token 效率

- [ ] **内容简洁**

  - [ ] 角色定义控制在 1,200-1,500 tokens 内
  - [ ] 无冗余或重复内容
  - [ ] 保持必要信息的同时避免啰嗦

- [ ] **示例按需加载**
  - [ ] 详细示例放在 examples/目录
  - [ ] 角色定义仅提供快速示例
  - [ ] 明确说明何时查看详细示例

### 3.5 一致性

- [ ] **与其他角色一致**

  - [ ] 格式风格统一
  - [ ] 术语使用一致
  - [ ] 质量标准对齐

- [ ] **与框架一致**

  - [ ] 符合框架设计原则
  - [ ] 与框架文档术语一致
  - [ ] 支持框架工作流程

- [ ] **无冲突**
  - [ ] 职责不与其他角色重叠
  - [ ] 输出不与其他角色冲突
  - [ ] 协作关系清晰无歧义
