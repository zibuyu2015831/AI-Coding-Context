# 自定义工具创建工作流

本工作流旨在指导 AI 在遇到特定场景时，创建高质量、标准化的自定义工具脚本，丰富项目的工具生态。

## 1. 触发条件

由于 AI 会话通常是独立的，无法跨会话追踪操作频率。因此，当满足以下**任一**特征时，即应主动创建工具：

- **复杂性 (Complexity)**:
  - 需要组合 3 个以上 Shell 命令（管道/重定向）才能完成。
  - 涉及复杂的正则表达式匹配或文本处理。
  - 需要编写 5 行以上的临时 Shell 脚本。
- **安全性 (Safety)**:
  - 涉及批量文件修改或删除（如批量重命名、清理日志）。
  - 需要 "Dry Run"（空跑）机制来确保安全。
- **通用性 (Utility)**:
  - 这是一个典型的通用开发任务（如：检查死链、统计代码行数、转换文件编码）。
  - 你判断该脚本在未来极有可能被再次使用。
- **用户指令 (User Intent)**:
  - 用户明确要求"写一个脚本"或"做一个工具"来解决问题。

## 2. 开发规范

### 2.1 语言选择

- **双模原则 (推荐)**: 尽量同时提供 Python (`tools/py/`) 和 Node.js (`tools/js/`) 版本。
- **单模例外**: 如果任务特定于某种语言环境（如仅用于 Python 项目的依赖分析），可只提供对应语言版本，但需在 `tools/README.md` 中注明。

### 2.2 依赖管理

- **零依赖原则**: 严禁引入需要安装的第三方库（如 `requests`, `pandas`, `lodash`）。
- **标准库**: 仅使用语言内置的标准库（如 `os`, `sys`, `json`, `fs`, `path`）。

### 2.3 错误处理

- **JSON 输出**: 尽量使用 JSON 格式输出结果，便于 AI 解析。
- **优雅失败**: 捕获所有可能的异常，输出包含 `error` 字段的 JSON，而不是直接 Crash 或打印堆栈信息。

### 2.4 命名规范

- 文件名使用 `snake_case` (Python) 或 `snake_case/camelCase` (Node.js，保持统一即可)。
- 文件名应清晰描述功能，如 `log_analyzer.py`, `config_migrator.js`。

## 3. 执行步骤

1. **需求分析**: 明确工具的输入、输出和处理逻辑。
2. **编写代码**:
   - 在 `tools/py/` 或 `tools/js/` 下创建文件。
   - 编写代码，遵循上述规范。
3. **本地验证**:
   - 运行脚本，测试正常情况。
   - 运行脚本，测试异常情况（如文件不存在、权限不足）。
4. **文档更新**:
   - 更新 `tools/README.md`，在表格中添加新工具。
5. **提交交付**:
   - 告知用户已创建新工具，并简述用途。
