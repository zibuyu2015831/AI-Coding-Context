# V3.0 方案建议：系统化文档审核框架 (019)

> **状态**: 🟢 已确认
> **版本**: v2.0（全面重设计版）
> **日期**: 2026-04-11
> **负责人**: Framework Team
> **真实案例来源**: `dev/某个项目的审查计划/`（SkillAtlas 项目 v2.1 审核体系）

---

## 1. 背景与必要性

### 1.1 问题根源

AICC V2.3 的文档维护机制依赖"代码变更事件触发增量更新"。然而以下场景无法被触发机制覆盖：

- **累积漂移**：每次变更微小、合理跳过，长期下来文档与代码已严重背离
- **隐性变更**：接口语义变化但签名未变，不触发 P0 更新
- **初始偏差传播**：AI 对某模块最初的理解就存在偏差，被"维护"保留并扩散
- **团队认知漂移**：文档描述的是"设计意图"，代码早已变成另一套实现

**结论**：文档全面审核是对增量更新的必要补充，并非可选项。

### 1.2 核心目标

让 `dev_docs/` 成为项目的**"可信真相源"**——新会话中的 AI 读完即懂、懂即可改，无需追问用户。

实现此目标必须同时满足双目标：

| 目标 | 定义 | 验收标准 |
|------|------|---------|
| **准确性** | 每条事实性断言必须与当前代码一致 | 能在源码中定位到 `文件:行号` |
| **完整性** | 文档必须覆盖模块的关键行为、隐性约束与历史坑点 | 新会话 AI 仅凭此文档能完成典型变更任务，无需追问 |

## 2. 设计理念

### 理念 1：过程全量物化（Files over Memory）

> **任何需要用户确认的内容，都必须先成为文件，再成为消息。文件是锚点，消息是过程。**

所有中间态（疑问、答复、裁定、修复计划、报告）全部写入磁盘，而非停留在会话内存。这一原则的直接收益：
- **断点可恢复**：无论主会话还是子代理中断，从目录文件即可完整恢复审核状态
- **用户异步参与**：用户可在 IDE 中直接编辑文件，不必实时在线
- **可追溯**：历史每一轮审核记录永久保留，支持对比与经验复用

### 理念 2：证据驱动（Evidence-Based）

每一条事实性断言必须附带源码证据：`文件路径:行号`，无证据即不写。不允许凭直觉或记忆填写文档。

### 理念 3：子代理隔离（Context Isolation）

单会话审核多份文档会导致**注意力衰减**——AI 在会话末尾对早期内容的把握已大幅下降。每份文档独立分配一个子代理，从结构上杜绝上下文污染。

### 理念 4：双方对齐驱动（Human-AI Alignment First）

每个关键阶段设置用户确认门禁，确保执行前 AI 与用户的理解完全一致：
```
发现 → 对齐 → 预演 → 执行 → 验证
```
杜绝"AI 自以为理解正确后径直修改"的风险。

### 理念 5：终极验收标准

> 在一个全新的会话中，AI 仅凭被审文档（加上 `AI_Coding_Context.md`）完成一次典型变更任务——能在不追问用户的情况下完成，则该文档验收通过。

其他所有过程指标（问题清单勾完、`verified_at` 更新等）均为必要条件，非充分条件。

## 3. 目录结构

### 3.1 `dev_docs/review/` 整体结构

```text
dev_docs/review/
├── sys_review_plan.md          # 审查规程文档（执行流程、Prompt 模板、触发机制）
├── sys_review_principles.md    # 核心原则文档（双目标、红线边界、验收标准）
├── REVIEW_LOG.md               # 全局进度总索引（跨轮次健康度看板）
└── rounds/                     # 审核轮次归档区（初始为空，含 .gitkeep）
    ├── 2026-Q2-baseline/       # 基线全量审核示例
    │   ├── _meta.md            # 本轮状态机（主会话唯一写入点）
    │   ├── _round_decisions.md # 跨文档裁定快照（全局共识锚点）
    │   ├── reports/            # Pass 1 深审报告（子代理写入）
    │   │   └── <doc>.report.md
    │   ├── questions/          # 结构化疑问（子代理写入）
    │   │   ├── <doc>.questions.md
    │   │   └── _merged.questions.md  # 阶段 1.5 合并产物
    │   ├── clarifications/     # 用户答复（用户在 IDE 中填写）
    │   │   └── <doc>.answers.md
    │   ├── fix_plans/          # 逐文档修复计划（计划子代理写入）
    │   │   └── <doc>.fix_plan.md
    │   └── consistency_check.md  # 阶段 4 跨文档一致性验证结果
    └── 2026-04-25_api_change/  # 事件触发定向小轮次
        └── ...
```

**轮次 ID 命名规范**：
- 基线全量审核：`YYYY-Q{1..4}-baseline`
- 事件/手动触发：`YYYY-MM-DD_<slug>`

**轮次目录永久保留**：作为中间产物归档，不在合并后删除。

### 3.2 两份核心模板文档的分工

AICC 提供两份模板，生成文档时根据项目实际情况微调：

| 文档 | 职责 | 关键内容 |
|------|------|---------|
| `sys_review_plan.md` | **How / When / Process** | 执行阶段流程、Prompt 模板、触发机制、轮次命名规范、并行度建议 |
| `sys_review_principles.md` | **What / Why / Standards** | 双目标定义、证据要求、审核范围边界、禁止事项、终极验收标准 |

## 4. 执行流程（八阶段协议）

```
阶段 0   → 准备与快照
阶段 1   → 并行深审（子代理，严格只读）
阶段 1.5 → 疑问汇集与去重（主会话）
阶段 2   → 多轮澄清循环（主会话 ↔ 用户，直到无空白条目）
阶段 2.5 → 多轮裁定快照生成（AI 起草 ↔ 用户修订，对齐为止）
阶段 3a  → 逐文档修复计划生成（计划子代理）
阶段 3b  → 用户审核修复计划（多轮，用户拍板）
阶段 3c  → 并行执行修复（执行子代理，严格遵循计划）
阶段 4   → 轻量复审（对照复查方法清单验证）
阶段 5   → 副产物归档 + 用户 git 合并
```

**角色分工总览**：

| 阶段 | 负责方 | 理由 |
|------|--------|------|
| 0 准备 | 主会话 | 唯一的全局初始化入口 |
| 1 深审 | **深审子代理**（每文档一个）| 上下文隔离，防止注意力衰减 |
| 1.5 疑问汇集 | 主会话 | 需要跨文档视角合并同质疑问 |
| 2 澄清循环 | 主会话 ↔ 用户 | 子代理无法实时对话 |
| 2.5 裁定快照 | 主会话起草 ↔ 用户审批 | 需要全局视角；用户最终拍板 |
| 3a 修复计划 | **计划子代理**（每文档一个）| 隔离上下文；携带三件套+裁定 |
| 3b 审核计划 | 用户 | 执行前的最终人工门禁 |
| 3c 执行修复 | **执行子代理**（每文档一个）| 严格按计划执行，不越权 |
| 4 复审 | 主会话 | 跨文档视角做最终一致性扫描 |
| 5 归档 + 合并 | 主会话 + 用户 | AI 归档，用户决定 git 提交 |

---

### 阶段 0：准备

1. 确认工作目录为仓库根
2. 加载 `AI_Coding_Context.md` 作为项目全景 primer
3. 记录 `git rev-parse HEAD` → 写入 `_meta.md`（代码快照锚点）
4. 创建本轮轮次目录骨架：`rounds/<round-id>/`
5. 在 `REVIEW_LOG.md` 中追加一条启动记录

---

### 阶段 1：并行深审（子代理，严格只读）

**原则**：每份目标文档分配一个独立子代理，上下文完全隔离。

**子代理输出**（必须写入磁盘，不得返回主会话内存）：
- `rounds/<round>/reports/<doc>.report.md`：问题清单与补全建议
- `rounds/<round>/questions/<doc>.questions.md`：需澄清的疑问

**子代理返回给主会话的内容**：仅限"产物路径 + 一句摘要 + 异常（若有）"

**report.md 结构**：
- **A. 准确性问题清单**：文档原文 vs 实际代码（含文件:行号），标注严重程度
- **B. 完整性补全建议**：缺失的关键内容及草稿，含源码依据
- **C. 疑问索引**：仅列编号和标题，详见 questions.md
- **D. 代码问题观察**：仅记录，不修复，含建议归档路径
- **E. 证据索引**：本次访问的主要源码文件

**questions.md 结构**（可打勾格式）：
```markdown
## Q1 - <一句话标题>
**触发条目**：A<编号> / B<编号>
**上下文**：文档现写 vs 代码现状（文件:行号）vs 已查历史资料
**具体问题**：...
**可能假设**：A) ... B) ... C) ...
**[ ] 已答复**
**答复**：<留空，等待用户>
```

**降级方案（无子代理工具）**：
- 提示用户手动为每份文档新开一个会话窗口
- 在每个子窗口中粘贴对应的 Pass 1 Prompt + 目标文档路径
- 执行完成后将产物文件复制到指定目录，再回到主会话继续

**并行度建议**：
- L1 核心文档（入口文档等）**单独一批**先做，确保全局一致性基准
- L2/L3 文档分批，每批 ≤4 个子代理并行

---

### 阶段 1.5：疑问汇集与去重（主会话）

1. 读取所有 `questions/*.questions.md`
2. 按话题聚类，识别跨文档同质疑问
3. 生成 `questions/_merged.questions.md`（合并视图 + 反向链接到原始文件）
4. 更新 `_meta.md` 文档状态表

---

### 阶段 2：多轮澄清循环（主会话 ↔ 用户）

**用户操作方式**：在 `_merged.questions.md` 或各 `*.questions.md` 中直接填写答复。

**每条疑问三态**：
- `[x]` 已答复 → 纳入修复范围
- `[~]` 搁置 → 本轮跳过，记录到 REVIEW_LOG 遗留项
- `[?]` 用户也不确定 → 保留原文，文档中加 `⚠️ 待确认` 标注

**循环退出条件**：所有条目均已脱离 `[ ]` 空白状态（无论哪种三态）。

**答复格式**：用户重点解释"为什么"（设计意图、历史决策），而非"是什么"（是什么可从代码读出）。

---

### 阶段 2.5：多轮裁定快照生成（主会话 ↔ 用户）

**目的**：生成 `_round_decisions.md`，作为阶段 3 所有修复子代理的**全局共识锚点**，从源头解决跨文档不一致问题。

**多轮对齐流程**：
```
AI 基于所有 report.md + answers.md 起草 _round_decisions_draft.md
       ↓
用户审查：直接在草稿上标注异议、修改内容、补充说明
       ↓
AI 响应：解释每条裁定的代码依据，或接受用户修正并更新草稿
       ↓
循环直到用户在 _meta.md 中显式批准 → 定稿为 _round_decisions.md
```

**`_round_decisions.md` 结构**：
```markdown
---
round: 2026-Q2-baseline
status: approved          # draft / under-review / approved
version: v2
approved_by: <user>
approved_at: 2026-04-11
---

## Part A：跨文档统一裁定（所有修复子代理必须遵守）
| 裁定 ID | 类型 | 裁定结论 | 代码证据 | 影响的文档 |
|--------|------|---------|---------|-----------|
| D-1 | 端口号 | API Gateway = 8080 | main.py:L42 | api_gateway, service_topology |
| D-2 | 术语 | 统一使用 "registry-service" | docker-compose.yaml:L17 | 全部 |

## Part B：各文档修复摘要（子代理行动范围指引）
| 文档 | 修复项数 | 关键修复描述 | 关联裁定 |
|------|---------|------------|---------|
| kafka_event_system.md | 3 | A2路径错误、B1补全容错 | D-1 |

## Part C：遗留问题（本轮不修改）
| 来源 | 状态 | 原因 | 本轮处理方式 |
|------|------|------|------------|
| Q5 [?] | 不确定 | 用户无法确认历史决策 | 文档加 ⚠️ 待确认 |
| B7 [~] | 搁置 | 需重构，本轮不处理 | 记录到 REVIEW_LOG |
```

---

### 阶段 3a：逐文档修复计划生成（计划子代理）

每份文档分配一个计划子代理，并行生成 `fix_plans/<doc>.fix_plan.md`。

**子代理输入（三件套 + 全局裁定）**：
| 输入文件 | 用途 |
|---------|------|
| 目标文档本身 | 了解当前内容 |
| `reports/<doc>.report.md` | 知道要改什么 |
| `clarifications/<doc>.answers.md` | 知道为什么这样改 |
| `_round_decisions.md` | 知道跨文档改动时用哪个说法 |

**`fix_plan.md` 结构**（逐条详细，消除歧义）：

```markdown
---
doc: kafka_event_system.md
round: 2026-Q2-baseline
status: pending_approval   # pending_approval / approved / rejected
planner: plan-subagent
planned_at: 2026-04-11
fix_count: 3
estimated_churn: medium    # low / medium / high
---

# 修复计划：<目标文档文件名>

## 计划概要
- 修复条目数：N（准确性 A 条 + 完整性补全 B 条）
- 不修复/遗留：M 条（含原因）
- 预估改动规模：小/中/大（约 N 行）
- 依赖裁定：D-X、D-Y

---

## FP-1：<一句话标题>
**来源**：report.md A2 | **关联裁定**：D-1

### 问题描述
<当前文档中的错误内容及其对 AI 理解的影响>

### 决策依据
- 代码证据：`<文件:行号>` 中写道 "..."
- 用户答复（Q<N>）："..."
- 关联裁定 D-X：...

### 修复方案（前/后对比）
**修改前（第 X-Y 行）：**
```
<原文内容>
```

**修改后：**

```
<新内容（含源码证据注释）>
```

### 复查方法
修复后，执行以下核查：
- [ ] 在文档中搜索"<旧值>"确认已替换
- [ ] 对照 `<文件:行号>` 确认文档与代码逐字一致
- [ ] 若涉及跨文档裁定，确认与 _round_decisions.md D-X 一致

---

## FP-2：...（同结构）

---

## 不修复项

| 来源 | 原因 | 本轮处理 |
|------|------|---------|
| B7 | 用户标注 [~] 搁置 | 原章节加 `<!-- TODO: 待重构后完善 -->` |
| Q5 | 用户标注 [?] 不确定 | 对应段落加 `⚠️ 此处设计意图待确认` |
```

---

### 阶段 3b：用户审核修复计划（多轮，用户拍板）

用户对每份 `fix_plan.md` 的操作选项：
- `[x]` 在每个 FP-N 打勾 → 批准该修复项
- ✏️ 直接修改"修复方案"内容 → AI 根据修改重新确认
- ❌ 标注"删除"或"本轮放弃" → 标记为 deferred
- 💬 在文件中提问 → 返回澄清循环

**门禁**：所有 `fix_plan.md` 全部达到 `approved` 状态后，方可进入阶段 3c。主会话在 `_meta.md` 审批总览表中维护每份文档的批准状态。

---

### 阶段 3c：并行执行修复（执行子代理）

**执行子代理的唯一权威输入**：对应的 `fix_plan.md`（只执行 `approved` 的 FP-N）。

**执行约束**：
- 只能修改指定目标文档，禁止写入任何其他文件
- 严禁修改代码文件
- 每条新增/修改的事实性断言必须附带源码证据
- 若发现 `fix_plan.md` 与代码现状存在冲突：**立即停止**，在 `_meta.md` 异常区写明冲突描述，等待用户裁定。不得自行修正计划。

**降级方案**：若无子代理工具，主会话按计划逐篇串行执行。

---

### 阶段 4：轻量复审

由于跨文档一致性已在阶段 2.5 前置裁定，且每个 FP-N 都有明确的复查方法，此阶段主要为**机械化验证**：

1. **逐条执行复查 checklist**：主会话逐条执行各 `fix_plans/*.fix_plan.md` 中的"复查方法"清单，确认执行子代理的修改已准确落地
2. **一致性扫描验证**：主会话快速扫描 `_round_decisions.md` 中的所有裁定，确认每条裁定已在涉及的文档中统一落地；将扫描结果写入 `rounds/<round-id>/consistency_check.md`（格式：裁定 ID → 涉及文档 → 检查结果 ✅/❌/⚠️，❌ 项需指明冲突位置并立即派发定向修复）
3. **终极验收**：随机抽 1 份文档，在全新会话中让 AI 仅凭此文档（加上 `AI_Coding_Context.md`）完成一次典型变更任务，通过则验收合格

---

### 阶段 5：副产物归档 + 用户合并

1. 代码问题（report.md D 章节）→ 归档到 `plans/bugfixes/<date>_<slug>.md`
2. 在相关文档中以"参见 BUG-N"形式交叉引用
3. 所有目标文档的 `verified_at` 更新为审核当日日期
4. 在 `REVIEW_LOG.md` 中追加本轮摘要与指向 `rounds/<round-id>/` 的链接
5. 本轮 `rounds/<round-id>/` 目录作为中间产物归档保留（永久）
6. **用户手动 `git add / commit / push`**（禁止 AI 自动提交）

---

## 5. 审核触发机制

### 5.1 时间触发（周期化审核）

| 频率 | 范围 | 说明 |
|------|------|------|
| **每季度一次** | 全量（所有目标文档）| 基线审核，跑完 Pass 1+2 完整流程 |
| **每月一次** | 抽样（随机 3 份 L2/L3）| 验证文档腐化速度，仅做 Pass 1 |

### 5.2 事件触发（必须做）

在以下事件发生时，对相关文档发起定向审核（至少 Pass 1）：

| 触发事件 | 必须重审的文档 |
|---------|--------------|
| 新增/删除服务或模块 | 入口文档、拓扑文档、API 文档 |
| 修改数据库模型 | 数据模型文档 + 对应服务文档 |
| 修改 API 路由 | API 文档 + 对应服务文档 |
| 修改核心配置文件 | 部署文档、拓扑文档 |
| AI 辅助编程中反复出现"文档与代码不符" | 被投诉的相关文档 |

### 5.3 手动触发

- 重要版本发布前
- 新成员 onboard 遇到文档歧义时

所有重审事件记录到 `REVIEW_LOG.md` 的"重审触发日志"章节。

## 6. 审核范围边界

### 6.1 目标文档（真相源）

位于 `dev_docs/` 顶层的技术规范文档，例如：
- L1 核心：主入口文档、服务拓扑、数据模型
- L2 关键：API 网关、事件系统、核心业务功能
- L3 支撑：存储、安全、搜索、部署

### 6.2 严格排除的目录

以下目录**不在**审核范围，原因是其内容是历史记录/过程产物，而非"描述代码现状"的真相源：

| 目录 | 性质 | 可读取（辅助）| 可修改 |
|------|------|------------|--------|
| `_analysis/` | 历史分析报告 | ✅ | ❌ |
| `knowledge/` | 经验知识库 | ✅ | ❌ |
| `plans/` | 开发与 Bug 修复记录 | ✅ | ⚠️ 仅允许追加新 bugfix |
| `review/` | 审核体系自身 | ✅ | ⚠️ 仅允许追加进度记录 |
| `thinking/` | 推理过程归档 | ✅ | ⚠️ 仅允许追加新归档 |

### 6.3 代码文件

**绝对禁止**：无论任何阶段，任何子代理或主会话均不得修改代码文件。审核发现的代码问题只能记录，不能就地修复。

## 7. 防线层次设计

```
Layer 1（发现）：子代理深审，严格只读   → 不会破坏任何现有内容
Layer 2（对齐）：多轮澄清 + 裁定快照    → 人机思路完全一致后才进入下一步
Layer 3（预演）：详细 fix_plan.md       → 用户在执行前完全清楚会发生什么
Layer 4（执行）：执行子代理严格遵循计划  → 不越权、不猜测、遇冲突立即停止
Layer 5（验证）：复查方法 + 终极验收     → 闭环确认，最终以"AI 新会话可用"为标准
```

## 10. 实现路径与集成方式

### 10.1 AICC 框架提供的内容

**两份模板文件**（存放于 `ai_coding_context/templates/review/` 目录下）：

| AICC 框架模板文件 | 生成到用户项目后的文件名 | 职责 |
|-----------------|----------------------|------|
| `review_plan_TEMPLATE.md` | `dev_docs/review/sys_review_plan.md` | 执行流程、Prompt 模板、触发机制 |
| `review_principles_TEMPLATE.md` | `dev_docs/review/sys_review_principles.md` | 双目标定义、禁止事项、验收标准 |

**三份 Prompt 模板**（内嵌在 `review_plan_TEMPLATE.md` 中，生成时一并带入）：
- `Pass1_Audit_Prompt`：用于深审子代理（阶段 1）
- `Fix_Plan_Prompt`：用于计划子代理（阶段 3a）
- `Pass2_Execute_Prompt`：用于执行子代理（阶段 3c）

### 10.2 AICC 文档生成时的行为

在为用户项目生成文档体系时，AICC 同时在 `dev_docs/review/` 目录下生成：
1. **`sys_review_plan.md`**：基于 `review_plan_TEMPLATE.md`，根据项目实际情况微调文档列表、分层策略、事件触发表，以及 Prompt 中的项目上下文描述
2. **`sys_review_principles.md`**：基于 `review_principles_TEMPLATE.md`，微调项目名、特殊约束
3. **`REVIEW_LOG.md`**：初始化空白总索引
4. **`rounds/.gitkeep`**：占位文件，确保 rounds/ 目录被 git 追踪

### 10.3 建议优先级

**P1（与 ADR 系统同级）**：两者都是"架构知识长期可追溯性"的核心组件。

## 11. 退出条件（一轮完整审核）

完成以下所有检查后，方可视为本轮审核结束：

- [ ] `rounds/<round-id>/` 目录结构完整，`_meta.md` 已写入启动元信息
- [ ] 所有目标文档均有对应的 `reports/*.report.md`
- [ ] 所有目标文档均有对应的 `questions/*.questions.md`
- [ ] `_merged.questions.md` 已生成并覆盖全部疑问
- [ ] 所有疑问条目均已脱离 `[ ]` 空白状态（已答复/搁置/不确定）
- [ ] `_round_decisions.md` 已被用户显式批准（_meta.md 中有记录）
- [ ] 所有需修订文档均有对应的 `fix_plans/*.fix_plan.md`，且已被用户批准
- [ ] 所有执行子代理均以"正常完成"或"异常已裁定"收尾，`_meta.md` 异常区为空或均已处理
- [ ] `consistency_check.md` 已生成且所有冲突均已修复
- [ ] 所有"代码问题观察"均已归档到 `plans/bugfixes/`
- [ ] 所有目标文档的 `verified_at` 已更新为审核当日日期
- [ ] `REVIEW_LOG.md` 已追加本轮摘要
- [ ] **终极验收**：随机抽 1 份文档，新会话 AI 仅凭此文档可完成典型变更任务，不追问用户
