# AI Coding Context 框架审查指南

本文档提供了 AI Coding Context 框架审查的标准化指南、方法和模板，可用于所有框架审查活动。

## 📋 审查背景与目标

### 背景

AI Coding Context (AICC) 框架是一个全面的 AI 辅助编程框架，自启动以来已完成多个版本迭代。为确保框架质量和持续发展，需要建立标准化的审查机制。

### 审查目标

1. **整体完整性验证**：确认整个框架的结构完整性和功能完整性
2. **架构一致性评估**：检查各组件之间的集成与协同工作情况
3. **问题全面检测**：识别潜在的技术缺陷、集成问题、文档不一致和性能瓶颈
4. **质量综合评估**：评估代码质量、文档质量、用户体验和系统稳定性
5. **价值实现分析**：验证框架是否达到预期的设计目标和用户价值
6. **未来发展建议**：基于审查结果提出框架未来发展的方向和改进建议

## 🔍 审查范围与方法

### 审查范围说明

AICC 采用三分支模型：**master**（终端用户、干净框架树）/ **dev**（集成测试，结构与 master 完全一致）/ **internal**（孤儿分支，承载全部 `dev/` 开发元数据，永不并入 master/dev）。`dev/` 树仅存在于 `internal` 分支。任何一次完整审查都必须明确选择"视角"，避免把"终端用户体验问题"与"开发工作区问题"混为一谈。

### 审核视角分层（V1.1 起）

| 视角 | 可见范围 | 审核目标 | 何时使用 |
|---|---|---|---|
| **A. 用户视角** | master/dev 用户可见树 | 模拟终端用户照着 `README.md` → `AI_ENTRY_POINT.md` 能否跑通；**任何对 `dev/` 路径的引用都视为用户可见树(master/dev)中指向 `dev/` 的引用——因 `dev/` 不在该分支，属断链/泄漏缺陷** | 评估上手路径、对外承诺与实现一致性、文档闭环 |
| **B. 完整性视角** | 用户可见树 + internal/dev/ | 交叉检查 实现 ↔ ADR ↔ FRAMEWORK_CONTEXT ↔ dev/plan 是否一致；验证设计意图是否在代码中落地 | 评估架构演进、设计-实现匹配度、自指一致性 |
| **C. internal/dev/ 卫生视角** | 范围：`internal` 分支的 `dev/` 树 | 审核目标：(1) `dev/` 自身组织清晰、无悬空内部引用；(2) `dev/` 仅存在于 `internal` 分支——`master`/`dev` 工作树不得出现任何 `dev/`、`FRAMEWORK_REVIEW*.md` 等开发元数据；(3) `master` 与 `dev` 结构一致，使 `git merge dev → master` 永远是干净 fast-forward；(4) 用户可见树(master/dev)中无任何指回 `dev/` 的引用泄漏。 | 评估开发工作区健康度、版本演进档案完整性 |

**与旧政策的关系**：v1.0 曾要求"跳过 dev/ 目录"——该政策仅在视角 A 下成立。v1.1 起三视角并存，依据视角决定可见范围，不再统一排除 dev/。

**视角使用原则**：

- 一次完整审查（Comprehensive round）应同时执行 A、B、C 三视角
- 每条问题在 `Issue_Tracking.md` 中必须标注其归属视角（便于按视角分类修复）
- 同一文件在不同视角下可能得出不同结论：例如 `core/design_decisions.md` 链接 `dev/architecture/decisions/` 在视角 A 是缺陷、在视角 B 是设计意图证据 —— **以视角 A 为优先**（用户体验是底线）
- 仅在专项审查（Component / Security / Performance scope）时可省略部分视角，需在 `Review_Plan.md` 中显式声明

### 整体架构审查

- **框架结构**：整体目录结构的合理性与逻辑性（按所选视角决定是否含 dev/）
- **模块划分**：各模块的功能划分与职责边界清晰度
- **版本管理**：版本迭代过程中的架构演进与一致性
- **设计原则**：框架设计原则的贯彻与实施情况
- **扩展性**：框架的扩展机制与未来发展规划的契合度

### 核心组件审查

- **agents/目录**：AI 角色库的实现质量与完整性，角色定义的准确性与一致性
- **config/目录**：配置系统的实现与集成情况，配置的灵活性与安全性
- **core/目录**：核心功能的实现质量，核心机制的稳定性与可靠性
- **tools/目录**：实用工具的实现与功能完整性，工具之间的协同性，**必须验证 Py/JS 双版本且零依赖约束**
- **workflows/目录**：工作流程定义的准确性与可执行性，**重点关注 Commit-Guided 更新 (018) 与互审机制 (013)**
- **ADR 系统**：架构决策记录的完整性，探针工具 (`why_tool`) 的集成有效性
- **复杂度仪表盘**：扫描器 (`complexity_scanner.py`) 的准确性与报告生成逻辑
- **templates/目录**：模板系统的完整性与可用性，模板质量与实用性
- **guides/目录**：指南文档的完整性与准确性
- **quality/目录**：质量管理机制与审查上下文 (`contexts/`) 的有效性
- **reference/目录**：参考资料的完整性与准确性

### 文档生态系统审查

- **文档完整性**：各层级文档的覆盖度与完整性，**包含强制摘要 (012) 的合规性检查**
- **文档一致性**：文档之间的交叉引用，以及与代码实现的一致性
- **文档维护**：验证 Commit 驱动的自动化同步机制是否按预期工作
- **特殊文档**：贡献指南、API 文档等关键文档的质量与完整性

### 系统集成与交互审查

- **组件间交互**：各组件之间的数据流与交互机制
- **依赖关系**：依赖关系的实现与管理的正确性
- **错误处理**：跨组件的错误处理与恢复机制
- **性能影响**：各组件对整体系统性能的影响
- **数据流**：系统内部数据流转的合理性与效率

### 用户体验与可用性审查

- **使用流程**：从用户视角评估完整使用流程的顺畅度
- **学习曲线**：新用户上手框架的难易程度与学习路径
- **错误提示**：系统错误提示的清晰度与指导性
- **反馈机制**：用户反馈收集与处理的机制
- **实际应用场景**：框架在真实编程场景中的适用性与效果

### 技术质量与安全性审查

- **代码质量**：各组件代码的可读性、可维护性与扩展性
- **双脚本模式 (V3.0 强制)**：验证所有工具脚本是否同时提供 Python 和 Node.js 版本
- **零依赖约束 (V3.0 强制)**：验证脚本是否仅使用标准库，严禁第三方库依赖
- **安全性**：框架的安全机制与潜在安全风险
- **可靠性**：框架在各类场景下的稳定性与容错能力
- **兼容性**：在不同环境、不同编程语言的兼容性

## 🤖 子代理委派策略 (Sub-agents Strategy)

为了提升审查效率并保持上下文纯净，主代理应根据任务特性委派子代理。AICC 在 `agents/runtime/` 下内置了多个专业角色；同时也可以使用宿主 IDE（Claude Code / Cursor / Codex 等）提供的通用 Explore / Search 子代理处理与角色无强绑定的批量任务。

| 委派任务模式 | 推荐角色（agents/runtime/） | 适用场景 |
| :--- | :--- | :--- |
| **批量合规性核查** | 通用 Explore / Search 子代理（无需特定角色） | 1. 检查 `tools/py/` 与 `tools/js/` 的文件对称性<br>2. 扫描所有 Markdown 文件验证 YAML 摘要 (012) 完整性<br>3. 静态检查脚本的 `import` 语句以验证"零依赖"约束<br>4. 全仓库 grep 死链/悬空引用 |
| **深度架构审计** | `code_reviewer.md` + `agents/development/architecture_analyst.md` | 1. 扫描代码库依赖图，对比 `dev/architecture/decisions/` 中的 ADR 记录<br>2. 识别跨组件的隐性耦合和违反职责边界的行为 |
| **安全红线检查** | `security_auditor.md` | 1. 验证 `core/security_rules.md` 红线在脚本/工作流中的落地<br>2. 敏感信息泄漏扫描<br>3. `git_safety_workflow` 执行情况抽查 |
| **文档与代码一致性** | `understanding_guardian.md` | 抽样验证文档对实现的描述是否与代码现状一致，发现"文档说一套实际另一套"的偏差 |
| **Commit 历史合规** | `commit_analyst.md` | 验证 Commit-Guided Documentation (018) 的实际运行情况：结构化 commit 比例、文档同步触达率 |
| **摘要规范扫描** | `summary_generator.md` 反向使用 | 抽样验证已生成的 YAML Frontmatter 摘要是否符合 `core/SUMMARY_FORMAT_SPEC.md` |

**委派原则**：

1. **输入明确**：给子代理提供清晰的审查清单和判定标准（最好是 yes/no 的二元判断）
2. **输出总结**：子代理只需返回"合规报告"或"异常清单"，无需在主会话中展示所有读取细节
3. **主代理决策**：主代理负责整合子代理的发现，并将其记录至 `Issue_Tracking.md`，标注归属视角

## 📊 审查报告结构模板

### 审查报告大纲

1. **执行摘要**

   - 审查概述与范围
   - 主要发现与关键结论
   - 优先改进建议
   - 整体风险评估

2. **框架整体评估**

   - 框架架构评估
   - 整体成熟度评级
   - 设计原则贯彻情况
   - 框架发展路径评估

3. **核心组件评估**

   - 各组件功能完成度与质量评级
   - 组件实现质量分析
   - 组件文档质量评估
   - 组件间依赖与交互分析

4. **文档生态系统评估**

   - 文档完整性与覆盖度评估
   - 文档质量与一致性分析
   - 文档维护与更新机制评估
   - 用户文档与实际功能匹配度

5. **系统技术评估**

   - 代码质量与架构评估
   - 系统性能与资源使用分析
   - 安全性与可靠性评估
   - 兼容性与可扩展性分析

6. **用户体验与可用性评估**

   - 用户旅程与使用流程分析
   - 学习曲线与上手难度评估
   - 真实场景适用性分析
   - 用户反馈与支持机制评估

7. **特定任务专项评估**（如适用）

   - 特定任务完成情况详述
   - 质量评级
   - 设计与实现一致性分析

## 🎯 审查成功标准

### 框架成熟度评级标准

#### 生产就绪级别 (A)

1. **架构完整性**：框架架构完整且一致，模块划分清晰
2. **功能完整性**：核心功能 100%实现，关键场景 100%支持
3. **代码质量**：代码质量评分 ≥90%，无高风险代码质量问题
4. **文档完整性**：文档覆盖度 ≥90%，准确性 ≥95%
5. **系统性能**：关键操作性能不低于设计标准的 90%
6. **安全性**：无高危安全漏洞，中危漏洞 ≤3 个
7. **用户体验**：用户流程顺畅度评分 ≥85%，学习成本 ≤3 天
8. **特定任务完成度**：所有特定任务 100%按设计实现

#### 可用但需改进级别 (B)

1. **架构完整性**：框架架构基本完整，模块划分较为清晰
2. **功能完整性**：核心功能 ≥90%实现，关键场景 ≥85%支持
3. **代码质量**：代码质量评分 ≥80%，无极高风险代码质量问题
4. **文档完整性**：文档覆盖度 ≥75%，准确性 ≥85%
5. **系统性能**：关键操作性能不低于设计标准的 80%
6. **安全性**：无极危安全漏洞，高危漏洞 ≤2 个，中危漏洞 ≤5 个
7. **用户体验**：用户流程顺畅度评分 ≥70%，学习成本 ≤1 周
8. **特定任务完成度**：所有特定任务 ≥90%按设计实现

#### 实验性级别 (C)

1. **架构完整性**：框架架构基本形成，模块划分有待完善
2. **功能完整性**：核心功能 ≥70%实现，关键场景 ≥60%支持
3. **代码质量**：代码质量评分 ≥70%，关键模块无严重代码质量问题
4. **文档完整性**：文档覆盖度 ≥60%，准确性 ≥75%
5. **系统性能**：关键操作性能不低于设计标准的 70%
6. **安全性**：无极危安全漏洞，高危漏洞 ≤5 个
7. **用户体验**：用户流程顺畅度评分 ≥60%，学习成本 ≤2 周
8. **特定任务完成度**：所有特定任务 ≥70%按设计实现

### 审查评估方法

#### 定量评估

- 代码质量评分：使用自动化工具评估代码可读性、复杂度、重复率等
- 文档覆盖度：文档覆盖的 API、功能、概念占总数的百分比
- 性能基准测试：关键操作的性能指标与设计标准的比值
- 安全漏洞扫描：使用安全工具扫描识别的漏洞数量和级别

#### 定性评估

- 架构一致性：专家评审框架设计与实现的一致性
- 用户流程顺畅度：用户测试评估使用流程的顺畅程度
- 功能完整性：功能测试评估功能的完整性和可靠性
- 学习成本：新用户上手所需时间的专家评估

#### 综合评级

- 定量评估占 60%权重，定性评估占 40%权重
- 各项指标加权计算得出总体框架成熟度评分
- 根据总体评分和关键指标确定框架级别

### 发布就绪性判断标准

#### 生产环境发布标准

- 框架评级达到 A 级别
- 无高危安全漏洞
- 关键功能 100%可用
- 核心文档完整且准确
- 通过真实场景测试

#### 预览/试用环境发布标准

- 框架评级达到 B 级别
- 无极危安全漏洞
- 核心功能 90%以上可用
- 主要文档完整
- 通过基础场景测试

#### 内部测试/实验环境发布标准

- 框架评级达到 C 级别
- 无极危安全漏洞
- 核心功能 70%以上可用
- 基础文档存在
- 基本功能可演示

## 🔁 审查文档管理机制

### 审查目录命名规范

- 格式：`YYYY-MM-DD_Version_Scope`
- 示例：`2025-12-18_V3.0_Comprehensive`
- 说明：日期*版本*审查范围（Comprehensive=全面，P0=P0 任务，Component=组件专项等）

### 审查文档索引维护

- 每次审查完成后更新 dev/quality/README.md
- 索引包含：审查日期、版本、范围、主要发现、改进建议状态
- 提供跨审查的对比和演进分析

### 审查文档生命周期

1. **创建**：审查启动时创建专用目录和基本文件
2. **更新**：审查过程中实时更新日志和阶段性报告
3. **完成**：审查完成后归档所有交付物
4. **追踪**：基于审查结果跟踪改进措施的落实情况
5. **对比**：新审查时与历史审查结果进行对比分析
6. **问题复查**：根据问题跟踪表进行问题复查和修复验证

### 多审查协同

- 各次审查保持独立性，通过索引文档建立关联
- 支持跨审查的指标对比和趋势分析
- 提供审查历史回溯功能，便于了解框架演进路径
