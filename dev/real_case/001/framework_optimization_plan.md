   - 方案模板中未包含 V3.0 特性的章节
   - 缺少强制性检查清单

4. **入口文档未说明**
   - `AI_ENTRY_POINT.md` 中未明确说明 V3.0 特性的使用方法
   - AI 不知道应该主动应用这些特性

#### 问题 2: 持续维护机制缺失

**根本原因分析**:

1. **方案模板中无维护章节**

   - 现有模板只关注文档生成，不关注后续维护
   - 缺少维护规划的强制性要求

2. **工作流未覆盖维护阶段**

   - `workflows/generation_workflow.md` 只到文档生成结束
   - 缺少维护工作流的说明

3. **更新触发机制未定义**
   - 没有明确的 P0/P1/P2 更新条件
   - 缺少健康度检查的标准流程

#### 问题 3: 配置目录位置混淆 ⚠️

**问题描述**:

用户期望配置信息存储在 `dev_docs/config/` 目录下，但框架实际生成的配置目录与 `dev_docs/` 同级，即 `project_root/config/`。

**现状对比**:

```
【用户预期】
project_root/
├── dev_docs/              # AI 文档目录
│   ├── config/            # ✅ 配置信息应该在这里
│   │   └── user_preferences.md
│   ├── api_layer.md
│   └── ...
└── AI_Coding_Context.md

【框架实际】
project_root/
├── config/                # ❌ 配置目录与 dev_docs 同级
│   ├── user_config.md
│   └── CONFIG_TEMPLATE.md
├── dev_docs/              # AI 文档目录
│   ├── api_layer.md
│   └── ...
└── AI_Coding_Context.md
```

**根本原因分析**:

**原因 1: 框架设计存在概念混淆**

框架中存在**两种不同性质的配置**，但未明确区分：

1. **框架运行配置** (`ai_coding_context/config/`)

   - **性质**: 框架自身的配置系统（V3.0 新特性）
   - **用途**: 控制框架行为（语言偏好、功能开关、AI 角色偏好等）
   - **位置**: 框架仓库根目录 `ai_coding_context/config/`
   - **文件**: `CONFIG_TEMPLATE.md`, `user_config.md`
   - **生命周期**: 框架级别，跨项目使用
   - **示例配置**: `documentLanguage: zh-CN`, `enableMutualReview: true`

2. **业务项目配置文档** (应该在 `dev_docs/configuration.md`)
   - **性质**: 业务项目的配置管理文档
   - **用途**: 说明项目如何管理配置（数据库、API、环境变量等）
   - **位置**: 应该在 `dev_docs/configuration.md` 文档中
   - **文件**: 配置文档（非配置文件本身）
   - **生命周期**: 项目级别，仅针对当前业务项目
   - **示例内容**: 环境变量说明、配置文件结构、部署配置等

**原因 2: FRAMEWORK_CONTEXT.md 中的目录结构说明产生混淆**

`dev/FRAMEWORK_CONTEXT.md` 第 311-354 行显示：

```text
典型用户项目结构（复制框架后的目标形态）

project_root/
├── config/                        # 🆕 配置管理系统 (V3.0)
│   ├── README.md                  # 配置系统使用指南
│   ├── CONFIG_TEMPLATE.md         # 配置模板
│   └── user_config.md             # 用户配置
├── dev_docs/                      # AI 文档目录
```

**问题**: 这个结构示例**误导**用户将框架的 `config/` 目录复制到业务项目根目录，导致：

- 框架配置（`user_config.md`）和业务项目文档混在一起
- 配置目录位置不符合用户直觉（应该在 `dev_docs/` 下作为文档）
- 用户不清楚这是框架配置还是项目配置

**原因 3: 框架复制策略不清晰**

框架没有明确说明：

- ❌ 哪些目录应该复制到用户项目？
- ❌ 哪些目录应该保留在框架仓库？
- ❌ `config/` 是框架级别还是项目级别？
- ❌ 用户应该如何管理业务项目的配置？

**原因 4: 配置文档化指南存在矛盾**

`guides/configuration_management.md` 第 437-540 行建议：

```markdown
在 dev_docs 中创建 `configuration.md`
```

这表明**项目配置文档应该在 `dev_docs/configuration.md`**，而不是复制框架的 `config/` 目录。

但 `FRAMEWORK_CONTEXT.md` 的目录结构示例又显示 `config/` 应该在项目根目录，造成**严重矛盾**。

**深层问题分析: 框架配置 vs 项目配置的边界不清**

| 维度               | 框架配置 (Framework Config)                              | 项目配置文档 (Project Config Doc)             |
| ------------------ | -------------------------------------------------------- | --------------------------------------------- |
| **性质**           | 框架行为控制                                             | 项目业务配置说明                              |
| **存储位置**       | `ai_coding_context/config/`                              | `dev_docs/configuration.md`                   |
| **是否复制到项目** | ❌ **不应该复制**                                        | ✅ 生成为文档                                 |
| **内容**           | 语言偏好、功能开关、AI 角色偏好                          | 环境变量说明、配置文件结构、部署配置          |
| **示例**           | `documentLanguage: zh-CN`<br/>`enableMutualReview: true` | 说明如何配置数据库连接<br/>说明环境变量的含义 |
| **作用对象**       | 控制框架如何生成文档                                     | 说明业务项目如何配置                          |
| **生命周期**       | 跨项目，全局生效                                         | 单项目，项目特定                              |

**影响**:

1. **用户困惑**: 不知道 `config/` 目录应该放在哪里，也不知道它的用途
2. **目录混乱**: 可能将框架配置和项目配置混在一起
3. **维护困难**: 更新框架时，用户配置可能被覆盖
4. **认知负荷增加**: 用户需要理解两套配置系统的区别

**结论**:

框架设计存在根本性的概念混淆，**需要明确区分并重新设计**：

1. **框架配置** (`ai_coding_context/config/`) - 保留在框架仓库，不复制到用户项目
2. **项目配置文档** (`dev_docs/configuration.md`) - 生成文档时自动创建，说明项目如何管理配置

### 2.2 优化策略

#### 策略 1: 工作流强制化

**核心思想**: 将 V3.0 特性从"可选"变为"强制"

**实施方式**:

- 在工作流中明确标注"[强制]"步骤
- 增加检查清单，确保每个特性都被应用

#### 策略 2: 模板标准化

**核心思想**: 更新所有模板，内置 V3.0 特性章节
