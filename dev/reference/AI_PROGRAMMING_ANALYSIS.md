## 一、文章核心洞察

### 1.1 Vibe Coding的本质：技术债的累积

**文章核心观点**:
> "Vibe Coding本质上是一种人类向大模型借的技术债"

**三种复杂性症状**:
1. **变更放大** (Change Amplification): 简单变更需要在多个层级修改
2. **认知负荷** (Cognitive Load): 需要更多时间掌握正确的上下文
3. **未知的未知** (Unknown Unknowns): 新session不知道"雷区"，直到触发错误

**根本原因**: AI编程的过程压缩导致复杂性指数级增长，远超人类编程

### 1.2 编程范式对比：战术式 vs 战略式

| 维度 | 战术式编程 | 战略式编程 |
|------|------------|------------|
| **目标** | 能跑就行，越快越好 | 产出卓越设计，确保有效工作 |
| **特征** | 短视，引入不必要复杂性 | 持续投入10-20%时间改进设计 |
| **结果** | 快速积累技术债，最终拖慢团队 | 短期投入，长期回报，速度超越战术式 |

**核心洞察**: Vibe Coding天然倾向于战术式编程，因为"代码能跑就是终极目的"

### 1.3 三个解决方法评析

#### 方法1: 对抗式编程（AI照镜子）
- 引入第三方监管（资深开发者 or 另一个AI）
- 消除单一模型的"鬼打墙"现象
- **局限**: 增加人力成本，流程复杂度上升

#### 方法2: 自动化代码审查（局部 vs 全局）
- 每天一次代码审查
- 早期发现冗余和依赖叠加
- **关键洞察**: **人类危险指令是最大风险源**

#### 方法3: AI作为思考工具而非生产工具
- 深入讨论系统设计思路
- 权衡不同方案优缺点
- 明确任务预期和边界
- 减少提示词模糊性

### 1.4 关键金句

> "面对指数级增长的复杂性，AI也许能做70%的执行工作，但剩下30%的架构、校验、调试、审查、维护等步骤目前还需要频繁人工介入"

> "生成式AI最大的优势是过程压缩，但软件系统本身的复杂性并没有降低"

## 二、框架契合度评估

### 2.1 解决"技术债累积"能力: ⭐⭐⭐⭐⭐ (5/5)

**完美契合度**:

**问题**: 快速交付 → 复杂性累积 → 技术债
**框架解决方案**: 项目检测 → 策略决策 → 方案生成 → 人工审核 → 分步执行 → 持续维护

#### 2.1.1 解决"变更放大"

**框架机制**:
1. **分层文档体系**:
   ```markdown
   主文档 (AI_Coding_Context.md)
     ├── API层规范 → 统一调用
     ├── 状态管理 → 统一流转
     ├── 路由管理 → 统一配置
     └── 命名规范 → 统一约定
   ```
   **价值**: API变更只需修改api_layer.md，全局自动遵循

2. **模块映射表**:
   ```markdown
   | 模块名 | 目录位置 | API文件 | Store文件 | 路由配置 |
   |--------|----------|---------|-----------|----------|
   | 用户管理 | src/views/user | src/api/user.ts | src/store/user.ts | ... |
   ```
   **价值**: 快速定位影响范围，避免遗漏

3. **更新触发机制** (core/update_triggers.md):
   ```markdown
   API接口变更 → 必须更新api_layer.md (P0)
   数据库Schema变更 → 必须更新database_schema.md (P0)
   核心配置变更 → 必须更新主文档+子文档 (P0)
   ```

**契合度**: ⭐⭐⭐⭐⭐ 完美解决

#### 2.1.2 解决"认知负荷"

**框架机制**:

1. **单一入口设计**:
   - 主文档作为唯一入口
   - 场景快速导航: "如何调用API?" → 直接链接到api_layer.md
   - 核心代码模式: 可直接复制的示例

2. **AI Rules集成**:
   ```markdown
   将规范配置到IDE → AI每次自动遵守 → 无需重复提醒
   ```

3. **知识库沉淀** (dev_docs/knowledge/):
   ```markdown
   - troubleshooting/ → 已解决问题
   - patterns/ → 架构模式
   - performance/ → 优化经验
   ```

**效果**: 认知负荷从"记住规范" → "查阅文档" → "AI自动遵守"

**契合度**: ⭐⭐⭐⭐⭐ 完美解决

#### 2.1.3 解决"未知的未知"

**框架机制**:

1. **AI编码禁忌** (主文档章节):
   ```markdown
   ⚠️ 禁止事项:
   1. 不要直接修改核心配置
   2. 不要引入新依赖未讨论
   3. 不要跳过错误处理
   4. 不要硬编码敏感信息
   ```

2. **问题发现与记录**:
   ```markdown
   生成方案必须包含:
   🔴 严重问题: [列表]
   🟡 警告问题: [列表]
   🔵 疑问事项: [列表]
   💡 优化建议: [列表]
   ```

3. **进度记录机制**:
   ```markdown
   记录内容:
   - 每个阶段时间
   - 关键架构特点
   - 遇到的问题和解决方法
   - 下一步计划
   ```

**效果**: 每个session都将问题沉淀，形成"雷区地图"

**契合度**: ⭐⭐⭐⭐⭐ 完美解决

### 2.3 战略式 vs 战术式编程在框架中的体现

| 维度 | 战术式编程 | 战略式编程 | 框架支持 |
|------|------------|------------|----------|
| 目标 | 能跑就行，越快越好 | 卓越设计，长期回报 | ✅ 强制方案优先 |
| 时间分配 | 100%编码 | 80%编码 + 20%设计 | ✅ 20%用于文档生成 |
| 复杂性管理 | 被动应对 | 主动预防 | ✅ 健康度检查 + 触发更新 |
| 知识沉淀 | 个人记忆 | 系统化文档 | ✅ dev_docs/knowledge/ |
| 决策方式 | 即兴决策 | 方案权衡 | ✅ plans/目录强制权衡 |

**框架本质是"强制战略式编程的工具"**：

```markdown
不使用框架:
用户: "实现用户登录功能"
AI: 直接生成代码
结果: 战术式编程 → 技术债累积

使用框架:
用户: "实现用户登录功能"
AI:
  1. 创建方案文档 (plans/features/..._login.md)
  2. 分析现有架构
  3. 设计方案 (技术选型/实施步骤/影响评估)
  4. 等待用户审核
  5. 执行编码
  6. 更新相关文档
  7. 沉淀知识到knowledge/

结果: 战略式编程 → 设计优先 + 文档沉淀 + 持续维护
```

**框架的"强制机制"**:
- ❌ 不能跳过方案直接编码
- ❌ 不能生成代码不更新文档
- ❌ AI不能臆测规范
- ✅ 必须人工审核方案
- ✅ 必须记录进度
- ✅ 必须沉淀知识

### 3.1 从"对抗式编程"得到的启发

#### 3.1.1 AI互审机制

```markdown
## 🤖 AI互审工作流 (V4.0新增)

### 角色定义
- **AI生成者** (Generator): 生成方案和代码
- **AI审查者** (Reviewer): 审查质量

### 工作流程
1. **生成阶段**
   AI生成者 → 生成方案 → dev_docs/plans/...

2. **审查阶段**
   AI审查者 → 读取方案 → 检查清单:
   ✓ 是否符合AI编码禁忌？
   ✓ 是否引入不必要复杂性？
   ✓ 是否有更好方案？
   ✓ 是否考虑错误处理？
   ✓ 是否考虑性能影响？
   ✓ 是否更新相关文档？
   → 输出审查报告

3. **决策阶段**
   人类 → 阅读方案 + 审查报告 → 决策

4. **编码阶段**
   AI生成者 → 生成代码
   AI审查者 → 审查代码 → 检查规范/复杂度/文档同步性
```

**价值**: 消除单一AI盲点，发现潜在问题，提升方案质量

### 引导清单

AI应在编码前探讨:

1. **问题本质** (5 Why分析法)

   方案A: 轻量级实现

   - 缺点: 扩展性有限

   - 优点: 可扩展，易于维护
   - 缺点: 开发慢(1天)，改动大
   - 适合: 长期使用

   方案C: 折中方案
   - 优点: 平衡速度和扩展性
   - 缺点: 需要后续重构
   - 适合: 快速上线+预留扩展
   ```

3. **边界定义** (明确范围)
   ```markdown
   ✅ 包含:
   - 用户登录界面
   - 用户名+密码验证
   - JWT token生成

   ❌ 不包含:
   - 第三方登录
   - 验证码功能
   - 记住密码
   ```

4. **风险评估** (提前识别)
   ```markdown
   潜在风险:
   - 密码存储安全性(高) → 使用bcrypt
   - JWT密钥管理(中) → 环境变量
   - 并发登录(低) → 暂不考虑
   ```

5. **成功标准** (可衡量)
   ```markdown
   验收标准:
   - ✅ 登录成功率 > 99%
   - ✅ 响应时间 < 200ms
   - ✅ 单元测试覆盖率 > 80%
   - ✅ 通过安全扫描
   ```
```

**价值**: AI作为思考伙伴，引导用户深入思考，降低返工概率

# ADR-003: 使用JWT进行用户认证

## 📋 决策信息
- **日期**: 2025-11-29
- **状态**: 已接受
- **参与者**: 张三(开发), 李四(架构)

## 🤔 背景与上下文
当前使用session进行认证，存在以下问题:
1. 不支持分布式部署
2. 移动端支持困难
3. 扩展性差

## 💡 决策
采用JWT(JSON Web Token)进行用户认证

## 🔍 考虑过的替代方案

### 方案A: 继续使用Session
- 优点: 实现简单，成熟稳定
- 缺点: 不支持分布式，移动端困难

### 方案B: OAuth 2.0
- 优点: 标准完善，生态成熟
- 缺点: 实现复杂，过度设计

### 方案C: JWT (推荐)
- 优点: 无状态，支持分布式，移动端友好
- 缺点: 需要管理token刷新，payload大小限制

## 📊 影响分析

### 正面影响
+ 支持微服务架构
+ 移动端友好
+ 性能提升（无需session查找）

### 负面影响
- 需要实现token刷新机制
- token泄露风险（需配合HTTPS）
- payload大小限制（不存储过多信息）

## ✅ 验收标准
- [x] JWT生成和验证功能
- [x] Token刷新机制
- [x] 安全存储（HttpOnly Cookie）
- [x] 单元测试覆盖率 > 90%

### 已实现
- src/auth/jwt.ts:15-50 - 实现JWT生成和验证
