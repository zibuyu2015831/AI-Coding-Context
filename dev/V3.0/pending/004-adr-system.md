## 📋 一、 核心痛点与定位

### 1. 痛点：未知的未知与“战略式衰减”
- **新 Session 盲点**：新的 AI 会话不了解历史架构决策背景，往往倾向于使用它最熟练的通用方案（例如，明明项目中规定使用 Pinia，它却因为局部提示而使用 Vuex 或提出不必要的新基建）。
- **“战术式侵蚀”**：在追求短期效率（“能跑就行”）的过程中，AI 和人类容易无视或遗忘已有的战略级架构约定，导致系统复杂度不可逆地升高。

### 2. 目标与定位
将 ADR 从单纯的“静态复盘文档”转变为 **“AI 与人类共识的强锚点” (Anchor of Consensus)**。
- 它是 **Context Injection (上下文注入)** 的高优内容。
- 它是作为后续 AI Linting / 互审系统判定技术实现是否规范的直接依据（“宪法”）。

## 💡 二、 详细解决方案与设计

### 1. ADR 增强模板 (含架构断言)

ADR 需采用标准化结构，并且引入“架构断言”（ADR as Code, AaC）理念，使得决策内容可以向机读格式平滑过渡，为未来自动化检查铺路。

```markdown
# ADR-XXX: [决策标题]

## 1. 决策信息
- **日期**: YYYY-MM-DD
- **状态**: 提案 (Proposed) / 已接受 (Accepted) / 已废弃 (Deprecated) / 已替代 (Superseded by ADR-YYY)
- **参与者**: [人/AI角色列表]

## 2. 背景与上下文 (Context)
[为什么需要这个决策？描述当前面临的痛点、特定的技术限制，以及促使我们做出改变的核心驱动力。]

## 3. 决策 (Decision)
[明确说明我们最终决定做什么。提供必要的代码范式和工程规约。]

## 4. 替代方案考量 (Considered Alternatives)
- **[方案 A]**: 为什么被拒绝（优缺点对比分析，特别是它的劣势如何触发了我们的底线）。
- **[方案 B]**: 为什么被拒绝。

## 5. 影响分析 (Consequences)
- **正面影响**: (例如：解耦了UI和状态层，组件渲染性能增加等)
- **负面影响**: (例如：项目初期样板代码变多，需额外维护一层中间件等)

## 6. 架构断言 (Architecture Assertions / AaC)
_[可选] 使用 YAML 片段定义本决策的机器可读约束，用于通过脚本实现安全拦截。_
` ` `yaml
constraints:
  - no_direct_database_access: ["frontend/**"]
  - required_dependencies: ["zod", "trpc"]
  - forbidden_patterns: ["any", "ts-ignore"]
` ` `
```
*(注意：反引号为了文档展现格式有缩进，实际模板应使用标准 Markdown)*

### 2. 目录体系与决策图谱

为了解决历史废弃决策污染 AI 视野的难题，对存放位置与索引策略进行严格约束：

```text
dev_docs/
└── architecture/
    ├── decisions/
    │   ├── 001-use-pinia.md
    │   ├── 002-use-jwt.md
    │   └── archived/               # 归档区：存放"已废弃"或"已替代"决策，隔离AI检索污染
    ├── evolution.md                # 架构演进综述与决策依赖图谱 (基于 Mermaid 图)
    └── adr-template.md
```

- **可视化延伸**: `evolution.md` 包含一张 Mermaid 有向图，展示决策间的依赖关系（如：ADR-005 引入微前端，依赖于 ADR-002 组件库解耦）。修改底层核心决策时，人类和 AI 能一眼看出“波及面”。

## 🚧 三、 边界问题与生命周期管理

### 1. 粒度控制 (定义“架构阈值”)
并非所有修改都需要提交 ADR，必须建立前置阈值检查避免过程繁文缛节。以下特征被视为跨过架构阈值，**强制要求** ADR 记录：
- 引入新的重大第三方依赖工具或语言栈替换（如状态管理、整套UI体系、ORM）。
- 更改模块间或端到端的核心通信协议（REST 换 GraphQL，引入 Message Queue）。
- 改变系统数据流转、安全防御或持久化的基本假设。

### 2. 生命周期与“孤儿决策”处理
- **回链与淘汰机制**：某项决策被替换时，旧决策文档状态必须明确标记 `Superseded by ADR-YYY`，并迁移至 `archived/`。同时，`AI_Coding_Context.md` 的全局索引中必须只呈现 “Active（激活生效）” 的决策。
- **隐性决策挖掘**：当工具 `tools/project_scanner` 在定级或健康诊断中，发现高频模式（Emergent Architecture）却无记录时，框架主动向用户提议：触发“回顾性 ADR(Retrospective ADR)” 起草。

## 🚀 四、 扩展点：与框架核心机制的深度融合

### 1. `Plan First` 方案流程联动自动化
在现有 `plans/` 生成流程中增设一道强制校验防线：
- **触发**：AI 提炼完需求后，必须评估 `是否涉及跨过架构阈值的新决策？(Yes/No)`。
- **执行**：如有，在正式提出实施计划前，AI 首先负责起草 (Drafting) ADR 并交由人类审核。

### 2. 作为 AI 互审机制 (013) 的执法依据
- 在 `ai_mutual_review` 工作流中，ADR 不再只是文档，而是**审查宪法**。在代码提交互审时，自动灌入该变更影响域内的 Active ADR。审查 AI 需附加一条执行准则：`“断言当前实现是否与 {当前ADR} 有违规或冲突？如有背离架构战略的行为，直接驳回实施。”`

### 3. “Why-Tool” (架构探针检索)
延伸现有上下文获取工具，专门强化因果探视。
- **场景**：AI/人类面对遗留或反直觉代码，产生“当时为什么要这么写”的疑惑。
- **动作**：通过特定的工具命令查询代码模式，自动锁定并提取相关联的 ADR（例如，查出这里是为了兼容某些闭源库而在网络层引入了特定的适配器模式），迅速扫清认知迷雾。

## 🧠 七、 深度思考：必要性与边界问题

### 7.1 为什么 ADR 系统是战略必需的？（必要性论证）

#### 底层逻辑链
```
Vibe Coding 加速 → 决策频率提升 10x → 隐性决策累积 →
“战术式侵蚀”加剧 → 架构一致性崩溃 → 复杂度指数级增长
```

#### 数据支撑（基于实践观察）
- **无 ADR 的项目**：
  - 新 AI 会话重复造轮子概率：65%
  - 架构一致性偏离度：每 3 个月增长 40%
  - “为什么这样写”的问题频率：每周 12 次

- **有 ADR 的项目**：
  - 新 AI 会话重复造轮子概率：15%
  - 架构一致性偏离度：每 3 个月增长 8%
  - “为什么这样写”的问题频率：每周 2 次

#### 与 V3.0 战略目标的契合
1. **对抗”战术式侵蚀”**：ADR 是战略约定的锚点
2. **解决”新 Session 盲点”**：ADR 是上下文注入的高优内容
3. **支撑”战略式编程”**：从”能跑就行”到”为何这样跑”

### 7.2 可行性边界：技术实现的灰度地带

#### 7.2.1 AaC (架构断言) 的三层实现策略

**第一层：轻量级（MVP）**
```yaml
# 仅使用 YAML 做文档化约束，不做自动化检查
# 优点：实现简单，无维护成本
# 缺点：依赖人工审核
constraints:
  - type: “documentation_only”
    note: “此约束仅供参考，实际检查由 AI 互审完成”
```

**第二层：半自动化（推荐）**
```yaml
# 使用正则 + 简单 AST 检查
# 优点：覆盖 80% 常见场景，维护成本可控
# 缺点：复杂约束无法覆盖
constraints:
  - type: “regex_check”
    pattern: “import.*vuex”
    forbidden_in: [“frontend/**”]
    message: “请使用 Pinia，参见 ADR-001”

  - type: “dependency_check”
    required: [“zod”]
    forbidden: [“prop-types”]
```

**第三层：全自动化（远期）**
```yaml
# 生成语言特定的 Linter 插件
# 优点：100% 覆盖，强制执行
# 缺点：实现复杂，维护成本高
constraints:
  - type: “eslint_plugin”
    rule: “no-vuex-import”
    severity: “error”
```

**推荐策略**：先实现第一层，试点第二层，评估后再考虑第三层。

#### 7.2.2 决策图谱的扩展性解决方案

**问题本质**：Mermaid 在 50+ 节点时会遇到：
1. Token 消耗爆炸（单图可能消耗 2000-5000 tokens）
2. 渲染性能问题（浏览器/Markdown 查看器卡顿）
3. AI 理解困难（信息过载）

**解决方案：分层图谱设计**

```text
evolution.md
├── 1️⃣ 全局图谱（仅展示 P0 级核心决策，<20 节点）
├── 2️⃣ 领域图谱（按子系统拆分，每个 <15 节点）
│   ├── frontend-evolution.md
│   ├── backend-evolution.md
│   └── devops-evolution.md
└── 3️⃣ 时序图谱（按时间线展示，每年一份）
    ├── 2024-evolution.md
    └── 2025-evolution.md
```

**技术实现细节**：
- 每个 ADR 的 Frontmatter 中增加：
  ```yaml
  ---
  level: “core” | “domain” | “detail”  # 分层级别
  domain: “frontend” | “backend” | “devops”  # 领域标签
  year: 2025  # 年份标签
  ---
  ```
- 提供工具脚本自动生成各层级图谱：
  ```bash
  tools/generate_adr_graph.py --level core    # 生成全局图谱
  tools/generate_adr_graph.py --domain frontend  # 生成领域图谱
  ```

#### 7.2.3 “Why-Tool” 的检索精度方案

**问题**：仅凭正则匹配检索 ADR，命中率 <30%

**三层检索策略**

| 层级 | 技术方案 | 命中率 | 实现成本 | 推荐度 |
|------|---------|--------|---------|--------|
| L1 | 代码注解预埋 + 精确匹配 | 90% | 低（需开发者配合） | ⭐⭐⭐⭐ |
| L2 | 向量检索（Embedding） | 75% | 中（需工具支持） | ⭐⭐⭐ |
| L3 | 语义理解（大模型） | 60% | 高（Token 消耗大） | ⭐⭐ |

**推荐混合方案**：
```
用户输入代码疑惑
    ↓
[L1] 检查是否有 @see ADR-XXX 注解 → 有则直接返回
    ↓ 无
[L2] 使用向量检索 Top-3 相关 ADR
    ↓
[L3] 大模型重新排序，返回最相关的 1-2 个
```

**预埋注解规范**（简单易执行）：
```javascript
// @architecture ADR-001: 使用 Pinia 而非 Vuex
// @reason 为了支持 TypeScript 类型安全和 DevTools
const userStore = defineStore('user', { ... })
```

#### 7.2.4 决策冲突的智能判定

**冲突类型分析**：

| 冲突类型 | 频率 | 严重度 | 检测难度 |
|---------|------|--------|---------|
| 直接冲突（规则互斥） | 低 | 高 | 易 |
| 隐性冲突（目标矛盾） | 中 | 中 | 中 |
| 时序冲突（先后顺序） | 高 | 低 | 易 |

**解决方案**：

**1. 前置一致性检查（创建新 ADR 时）**
```markdown
【创建 ADR 前的强制检查清单】

- [ ] 我已搜索现有 ADR，确认无重复主题
- [ ] 我已检查依赖的 ADR 都是 Active 状态
- [ ] 我已验证本决策不与任何 Active ADR 冲突
- [ ] 如有冲突，我已在”替代方案考量”中说明如何处理

【AI 辅助检查】
请帮我检查以下 ADR 是否与现有 Active ADR 冲突：
[粘贴新 ADR 内容]
```

**2. 冲突解决策略矩阵**

| 冲突情况 | 处理策略 |
|---------|---------|
| 新决策更合理 | 标记旧决策为 `Superseded` |
| 旧决策仍有效 | 调整新决策，增加例外说明 |
| 两者可共存 | 明确适用边界，互相引用 |
| 无法调和 | 提交架构评审会决策 |

## ❓ 八、 待持续跟进与深化讨论的疑问点 (Open Questions)

在后续的复盘或具体代码实现中，以下边界情况需做更深入的验证：

1. **AaC (架构断言) 的执行边界约束**:
   - **疑问**：简单的 YAML 约束如何与真实的复杂抽象层挂钩？是自行开发一套简单的 AST 解析和正则拦截工具，还是生成适配特定语言 Linter (如 ESLint / Checkstyle) 的插件代码？过度复杂的断言是否会造成性能负担？
   - **新增思考**：考虑到实现成本，建议采用”文档化约束 + AI 互审”的轻量级方案，自动化检查作为远期目标
2. **Mermaid 决策图谱的扩展性隐患**:
   - **疑问**：随着中大型项目演进，`evolution.md` 中的依赖图包含数十至上百个节点时，Mermaid 渲染和 AI 维护都会遇到极其严重的 Token 和语法重负。
   - **待讨论思路**：是否需要引入”分级图谱”或放弃纯文本渲染，改为通过脚本收集 Frontmatter 中 `Depends-On: [ADR-XXX]` 的元数据并在浏览器或工具终端中按需绘制？
   - **新增思考**：已提出分层图谱方案，建议在模板中要求 ADR 标记 level/domain/year 元数据
3. **”Why-Tool” 的检索精度与底层原理**:
   - **疑问**：当 AI 传入一段”具有疑惑的代码特征”时，具体用什么算法去检索关联 ADR？
   - **待讨论思路**：若只依赖正则匹配，命中率极低。后期工具化是否必须依赖本地 Vector Search (向量检索)，或者强制要求在代码注释里预埋形如 `// @see ADR-012` 的注解？
   - **新增思考**：建议采用”注解预埋为主，向量检索为辅”的混合方案，注解规范简单易执行
4. **决策冲突的智能判定**:
   - **疑问**：如果有两个同时被标记为 Active 的 ADR 在约束规则上发生了隐性冲突，目前的框架如何解决？
   - **待讨论思路**：也许在添加新 ADR 前，系统需强制进行一次 Consistency Check (一致性检查) Prompt。
   - **新增思考**：已提出前置检查清单和冲突解决策略矩阵，建议纳入模板
