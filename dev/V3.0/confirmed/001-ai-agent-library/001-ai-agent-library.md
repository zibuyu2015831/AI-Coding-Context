# 001 - AI 角色库 (Agent Library)

**优先级**: P0 ⭐ (基础设施)  
**状态**: 🟢 已完成 (Completed)  
**完成日期**: 2025-12-01  
**预估工作量**: 8-12 天  
**来源**: 用户洞察 + 专业化分工需求  
**被依赖**: 013 (AI 互审), 011 (文档谬误修复), 012 (强制文档摘要)

---

## 📋 问题描述

### 为什么是 P0 基础设施？

> **关键洞察**: AI 角色库不是一个独立功能，而是 V3.0 多个优化点的**共同基础设施**。

**被依赖的优化点**:

1. **013 (AI 互审机制)** - 需要 `plan_reviewer` 角色
2. **011 (文档谬误修复)** - 需要 `doc_fixer` 角色
3. **012 (强制文档摘要)** - 需要 `summary_generator` 角色

**结论**: 必须优先实现，否则其他优化点无法落地。

### 核心痛点

1. **缺少标准化的专业 AI 角色**

   - 用户需要自己编写复杂的 prompt
   - 每次都要重新定义角色和职责
   - 输出质量不稳定

2. **框架运行时缺少专业角色支持**

   - 文档生成、审查、修复都使用通用 AI
   - 缺少专业化的视角和标准
   - 质量不够高

3. **知识无法复用**
   - 好的 prompt 无法跨项目使用
   - 团队内部无法共享最佳实践
   - 重复劳动

### V2.3 现状

- ❌ 没有角色库概念
- ❌ 所有任务使用通用 AI
- ❌ 缺少专业化的输出规范

---

## ⚠️ 风险与疑问

### ✅ 已解决的问题 (基于 ai-coding-prompt 项目分析)

#### 1. ✅ 角色定义的粒度

**答案**: 采用**三级粒度模型**

```
分类层 (runtime/development/language_specific)
  └── 角色层 (如 plan_reviewer, code_reviewer)
      └── 清单层 (功能完整性检查、技术方案符合性检查...)
```

**具体方案**:

- **粒度原则**: 一个角色 = 一个专业领域（如测试、审查、设计）
- **初始数量**: P0: 10 个，P1: 8 个，P2: 4 个，**总计约 22 个**（参考项目验证过的规模）
- **避免混乱**: 清晰分类 + 统一命名 + 完善索引

**来源**: ai-coding-prompt 项目采用 8 层 22+角色架构，验证了这个粒度的有效性

---

#### 2. ✅ 角色调用机制

**答案**: 提供**三种调用方式**，满足不同场景需求

**方式 1: IDE 集成调用** (推荐)

```markdown
用户将角色定义复制到 AI IDE 的 agent 配置中

- 优点: 利用 IDE 原生功能，用户体验最好
- 适用: Claude Desktop、Cursor、Windsurf 等支持 agent 的 IDE
- 使用: 直接通过 IDE 的 agent 切换功能调用
```

**方式 2: 框架 Rules 调用**

```markdown
在 AI_RULES.md 中列举所有可用角色

- AI 在必要时主动提醒用户可使用的角色
- 示例: "检测到您在设计技术方案，建议使用 @角色:架构分析师"
```

**方式 3: 自然语言调用**

```markdown
在 AI_Coding_Context.md 顶层文档中列举角色清单

- 用户: "请使用代码审查员角色审查这段代码"
- AI 自动加载对应角色定义
- 最灵活，无需特殊语法
```

**综合策略**: 三种方式并存，用户根据喜好选择

### ❓ 待讨论的新问题

基于对 ai-coding-prompt 项目的分析，发现以下**4 个新问题**需要讨论：

#### 1. ❓ 角色的语言特定性

**问题**: ai-coding-prompt 项目高度偏向 Java/Spring Boot，我们如何平衡通用性和专业性？

**讨论点**:

- 是否需要为每种语言创建专属角色？
- 如何处理语言通用的角色（如 architecture_analyst）？
- 是否提供"基础版+语言增强版"的模式？

#### 2. ❓ 角色的更新机制

**问题**: 角色定义会随着最佳实践演进，如何管理更新？

**✅ 解决方案**: **框架维护者主导，用户反馈驱动**

```markdown
更新流程:

1. 用户反馈 → 2. 框架作者评估 → 3. 角色更新 → 4. 框架版本发布

具体机制:

- 角色一旦定义好、测试好就比较稳定
- 用户可以微调自己项目的角色副本，但不推荐自定义
- 框架作者吸收用户反馈意见，在框架更新时完成角色更新
- 通过版本号(v1.0 → v1.1)追踪角色演进
```

**用户微调 vs 框架更新**:

- ✅ **框架更新**: 由框架作者负责，保证质量和一致性
- ⚠️ **用户微调**: 允许但不推荐，用户自行承担维护责任
- 📌 **反馈通道**: 用户通过 GitHub Issues 或 Discussions 提交改进建议

| 单个角色定义           | ~1,200 tokens       | 完整角色文档    |
| 角色清单（22 个）      | ~1,500 tokens       | 仅名称+简短说明 |
| 完整 AI_Coding_Context | ~5,000-8,000 tokens | 作为对比        |

**加载策略**:

```markdown
策略 1: 框架运行时预加载

- 只预加载必需的角色（如 plan_reviewer 用于 001）
- 消耗: ~1,200 tokens
- 频率: 每次会话 1 次

策略 2: 用户主动调用

- 用户明确要求时才加载："@角色:代码审查员"
- 消耗: ~1,200 tokens/次
- 价值: 高，用户明确需要

策略 3: 智能提示

- 在 AI_Coding_Context 中列举角色清单
- 消耗: ~1,500 tokens（仅清单，不加载详情）
- 频率: 随主文档加载，不重复
```

**结论**: ✅ Token 消耗不大，完全可接受

- 按需加载，不是全部加载
- 相当于一个中等规模的子文档
- Token 换专业性，ROI 高

#### 4. ✅ 角色的测试和验证

**问题**: 如何确保角色定义确实能产生预期的效果？

**✅ 解决方案**: **信任大模型 + 用户反馈驱动**

```markdown
质量保障策略:

1. 信任大模型定义的角色能力
2. 依赖用户使用反馈发现问题
3. 通过版本迭代持续优化
4. 不建立复杂的测试机制（投入产出比低）
```

**理由**:

- ✅ **成本考虑**: 建立完整测试机制成本高
- ✅ **信任基础**: 基于成熟项目（89.2% AI 编码率）改造的角色
- ✅ **快速反馈**: 用户实战中的反馈更有价值
- ✅ **敏捷迭代**: 根据反馈快速优化更高效

**简化的验证流程**:

```markdown
1. 角色创建: 遵循标准格式和检查清单
2. 同行评审: 其他开发者简单 review
3. 实战试用: 小范围试用收集反馈
4. 迭代优化: 根据反馈改进
5. 正式发布: 移至 confirmed/
```

**暂不考虑**:

- ❌ 自动化测试用例
- ❌ A/B 测试机制
- ❌ 量化指标体系
