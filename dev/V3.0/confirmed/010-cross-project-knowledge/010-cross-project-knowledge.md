## 📋 问题描述

### 痛点
多个项目有相同的架构模式、问题解决方案和最佳实践，但每个项目都重新编写相同的文档，导致：

- **知识重复**：每个项目都有类似的架构文档
- **维护负担**：一个模式变更需要更新多个项目的文档
- **一致性问题**：不同项目对同一模式的实现细节可能不一致
- **知识流失**：项目结束后，knowledge 目录中的宝贵经验难以在其他项目中复用

---

## 💡 核心解决方案

### 核心创新思路
将项目的 knowledge 目录设计成独立的 Git 仓库，通过云端地址引入，实现知识在不同项目间的流转和复用。

#### 架构设计理念
```
AICC 框架 ←→ 项目代码 ←→ 共享知识库（云端 Git 仓库）
```
- **项目级知识**：保留在项目本地的 knowledge 目录，记录项目特定经验
- **共享级知识**：存储在云端 Git 仓库，包含通用架构模式、最佳实践、问题解决方案
- **自动匹配**：AICC 在分析项目时，自动识别可复用的共享知识

#### 知识仓库标准化结构

```text
shared-knowledge-repo/
├── .aicc/                 # AICC 配置目录
│   ├── metadata.json     # 知识库元数据（版本、贡献者、标签）
│   ├── schema/         # 知识结构定义
│   ├── taxonomies/       # 分类体系定义
│   ├── rules/          # 质量检查规则
│   └── templates/      # 知识模板
├── fundamentals/          # 基础知识（语言无关、通用原则）
├── languages/         # 编程语言特定知识
├── frameworks/        # 框架特定知识
├── platforms/       # 平台特定知识
├── databases/      # 数据库特定知识
└── case-studies/    # 完整案例研究
```

详细架构设计请参考 [architecture-design.md](./architecture-design.md)

知识类型图谱：
- **规范性知识**（Prescriptive）**：架构模式、编码规范、流程规范

- **渐进式进化**：从微小调整到重大变更的分级处理

| 场景 | 无复用 | 有复用 | 节省 |
|------|--------|--------|------|
| 新项目启动 | 重新编写 20+ 篇架构文档 | 复用共享知识 | **约 70 小时** |
| 技术方案评审 | 从零调研 | 引用已验证模式 | **约 5 小时/次** |
| 问题排查 | 重复搜索解决方案 | 直接查询知识库 | **约 3 小时/次** |

### 2. 提升质量

- **架构一致性**：团队成员使用统一的架构模式，减少"各做各的"问题
- **最佳实践**：共享知识库包含经过验证的解决方案，减少踩坑
- **代码质量**：相同的编码规范和设计模式贯穿所有项目

### 3. 降低风险

- **知识不丢失**：项目结束后的经验自动沉淀到共享库
- **新人快速上手**：新成员可以通过共享知识库快速了解团队规范
- **版本可追溯**：Git 版本控制确保每次变更可回溯

### 4. 团队协作

- **跨项目学习**：A 项目的经验可以快速分享到 B 项目
- **统一标准**：所有项目使用相同的架构规范和技术选型
- **知识众创**：团队成员可以共同维护和贡献知识

## 🚀 快速开始

### 场景 1：使用共享知识库（新项目）

```bash
# 1. 配置共享知识库（项目首次使用）
node tools/js/knowledge_cli.js config \
  --shared https://github.com/your-org/shared-knowledge.git

# 2. 启用共享知识
node tools/js/knowledge_cli.js enable-shared

# 3. 设置匹配策略（可选，默认 local-first）
node tools/js/knowledge_cli.js strategy --mode hybrid

# 4. 查看配置状态
node tools/js/knowledge_cli.js status
```

**效果**：文档生成时，AICC 自动从共享知识库中匹配相关内容注入文档。

### 场景 2：将本地知识贡献给团队

```bash
# 1. 初始化本地知识为共享知识库
node tools/js/knowledge_cli.js init --as-shared

# 2. 验证初始化结果
node tools/js/knowledge_cli.js status

# 3. 发布到云端（需先在 GitHub 创建空仓库）
node tools/js/knowledge_cli.js publish \
  --remote https://github.com/your-org/team-knowledge.git \
  --branch main
```

**效果**：团队其他成员可以通过 config 命令使用你的知识。

### 场景 3：保持知识同步

```bash
# 定期更新共享知识库
node tools/js/knowledge_cli.js update-shared

# 或强制更新（忽略本地变更）
node tools/js/knowledge_cli.js update-shared --force
```

## 📖 详细使用指南

### 1. 配置文件详解

知识库配置保存在 `.aicc/config.yml`：

```yaml
knowledge:
  # 本地知识库位置
  local_path: dev_docs/knowledge
  
  # 共享知识库配置
  shared:
    enabled: true
    repo_url: https://github.com/your-org/shared-knowledge.git
    branch: main
    cache_path: .aicc-cache/shared-knowledge
    last_updated: "2026-04-15T10:30:00Z"
  
  # 匹配策略：local-first | shared-first | hybrid
  match_strategy: local-first
  
  # 匹配相似度阈值 (0-1)
  match_threshold: 0.6
```

### 2. 匹配策略说明

| 策略 | 适用场景 | 说明 |
|------|----------|------|
| `local-first` | 项目有独特知识 | 本地知识优先，共享知识作为补充 |
| `shared-first` | 新项目/标准化项目 | 共享知识优先，确保遵循标准 |
| `hybrid` | 混合场景 | 根据相似度自动选择，保留最佳匹配 |

### 3. 知识引用语法

在文档中引用共享知识：

```markdown
<!-- 引用架构模式 -->
:::knowledge-ref pattern:mvc-architecture :::

<!-- 指定编程语言 -->
:::knowledge-ref pattern:error-handling language:python :::

<!-- 引用问题解决方案 -->
:::knowledge-ref problem:api-timeout context:microservice :::
```

### 4. 排除缓存目录

首次配置后，确保 `.gitignore` 包含缓存目录：

```
# AICC 知识库缓存
.aicc-cache/
```

## 🧠 决策依据与设计理念

### 1. 方案对比

| 方案 | 优点 | 缺点 | 适用场景 |
|------|------|------|----------|
| **独立 Git 仓库** | 成熟技术、版本控制、远程协作 | 需要单独维护 | 所有场景，推荐 |
| **企业知识库系统** | 功能强大、权限管理完善 | 成本高、学习曲线陡 | 大型企业 |
| **云存储服务** | 简单易用、成本低 | 缺乏版本控制和协作功能 | 小型团队、简单场景 |

### 2. 与 V3.0 战略契合点

1. **战略式编程**：确保跨项目的战略一致性
2. **知识沉淀**：将项目经验提升到企业级
3. **可扩展团队**：支持跨项目协作和知识共享
4. **持续维护**：Git 仓库提供完善的版本控制和更新机制

| 风险 | 等级 | 表现 | 缓解措施 |

## ⚠️ 尚存疑问与待解决问题

### 1. 知识仓库的默认配置
✅ **已确认方案**：提供官方**空仓库模板**（GitHub 仓库）
- 提供包含 .aicc/ 配置和标准目录结构的空模板
- 用户可 fork 后自定义内容，或从零开始创建
- 降低维护成本，保持灵活性
- 仓库地址：`https://github.com/aicc-framework/knowledge-template`

### 2. 知识贡献的激励机制
✅ **已确认方案**：不实现复杂激励机制，提供贡献指南
- 激励机制属于团队管理和文化范畴，框架只提供基础设施
- 提供 `CONTRIBUTING.md` 模板，说明贡献流程和质量要求
- 通过知识使用统计（可选功能）间接实现激励追踪

### 3. 知识的语言兼容性
✅ **已确认方案**：按语言分类存储，代码示例与语言绑定
- 这是架构设计核心原则（第 2 层 languages/）
- 每个知识条目可包含多个语言的代码示例
- 支持语言：JavaScript, TypeScript, Python, Java, Go, Rust, PHP, Ruby, C/C++

### 4. 知识库的存储方式
✅ **已确认方案**：**只支持 Git 仓库**，不实现云存储
- Git 提供成熟的版本控制、协作和离线使用能力
- 云存储（S3/OSS）增加复杂性，与 AICC 的 Git 工作流不契合
- 本地缓存机制解决网络依赖问题

## 📝 思考过程记录

### 方案设计的演变
1. **最初想法**：共享知识目录在同一代码库下（子目录）
2. **用户创新思路**：将 knowledge 目录设计成独立 Git 仓库
3. **架构优化**：标准化目录结构，支持多语言代码示例
4. **实现方案**：分阶段开发，逐步完善功能
5. **自进化系统**：用户提出框架自进化、自迭代的系统

### 关键决策点
1. **Git 仓库 vs 其他方案**：Git 提供了成熟的版本控制和协作功能
2. **标准化结构 vs 自由结构**：标准化结构提升了知识匹配和复用效率
3. **渐进式采用 vs 强制使用**：允许用户选择是否使用共享知识库
4. **混合模式 vs 单一模式**：平衡了一致性和响应性
5. **自进化系统**：通过设置入库流程，自动检测和扩充框架

- ✅ 支持通过 Git 仓库地址引入共享知识
- ✅ 实现知识匹配和引用机制
- ✅ 提供知识贡献引导
- ✅ 支持知识版本管理
- ✅ 实现本地缓存和离线使用
- ✅ 框架自进化系统（可选）
- ✅ 支持将本地 knowledge 目录初始化并发布为共享知识库
- ✅ 提供完整的知识库创建、初始化和发布流程
- ✅ 支持知识从本地到云端仓库的完整生命周期管理

- ✅ 知识仓库拉取时间 < 30 秒（10MB 以下仓库）

- ✅ CPU 使用率 < 20%（单线程）

- ✅ 版本兼容性检查准确率 > 85%

- ✅ 框架适配检测准确率 > 95%
