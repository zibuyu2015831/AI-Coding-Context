# SkillAtlas 文档体系审核计划

> **版本**: v2.1（子代理驱动版 + 中间产物持久化）
> **修订时间**: 2026-04-10
> **适用工具**: Claude Code / opencode 等支持子代理（Agent/Task 工具）的 CLI
> **执行模型**: 多阶段并行子代理 + 主会话编排 + 轮次目录持久化
> **配套文档**: `核心原则说明.md`

---

## 0. 版本变更说明

### v1.0 → v2.0 的变化

| 变化点 | v1.0 | v2.0 |
|--------|------|------|
| 执行模型 | 单会话串行审核 21 份文档 | 主会话编排 + 并行子代理（每文档一个） |
| 审核目标 | 只做"准确性验证" | **准确性 + 完整性补全** 双目标 |
| 与代码的关系 | 只读、只修文档 | 只读代码、只修文档，但**必须**记录发现的代码问题 |
| 用户交互 | 事后审阅报告 | Pass 1 后集中澄清、Pass 2 前注入答复 |
| 副产物 | 进度记录 + 修订 | 进度记录 + 修订 + `thinking/` + `plans/bugfixes/` |
| 审核范围 | 21 份（含 `_analysis`/`plans` 等）| **13 份**（严格排除非事实性目录）|
| 生命周期 | 一次性 | 周期化（含触发条件） |

v2.0 的目的是：在保留方式一的"系统性覆盖"优势的同时，通过子代理隔离上下文，结构性地解决"单会话注意力衰减"，并通过两遍协议近似方式二的"深审 + 交互补全"效果。

### v2.0 → v2.1 的增量修订

v2.0 的"汇集与澄清"链路仍依赖主会话的内存——Pass 1 报告只"返回"给主会话，几十条疑问在消息流里一次性呈现，用户无法逐条确认，Pass 2 之前也没有"推荐修复方案"可 review。v2.1 的目标是把这一切**物化到磁盘**，并引入两个新的 `.5` 阶段：

| 变化点 | v2.0 | v2.1 |
|--------|------|------|
| Pass 1 产物载体 | 返回主会话内存 | 写入 `rounds/<round>/reports/<doc>.report.md` |
| 疑问载体 | 混在报告里 | 独立 `rounds/<round>/questions/<doc>.questions.md`，可打勾 |
| 跨文档疑问去重 | 无 | 阶段 1.5 主会话合并为 `_merged.questions.md` |
| 用户答复载体 | 会话消息 | `rounds/<round>/clarifications/<doc>.answers.md`（Q&A 文件） |
| 用户确认粒度 | 一次性批量 | 按文件、逐条，可分多轮 |
| 重写前预览 | 无 | 阶段 2.5 方案子代理生成 `proposals/<doc>.proposal.md`，用户批准后才进入 Pass 2 |
| Pass 2 输入 | 报告 + 澄清（内存）| 只读 `proposal.md`（不得偏离）|
| 断点续审恢复 | 依赖主会话上下文 | 读取 `rounds/<round>/` 目录即可恢复全部中间态 |
| 跨文档一致性 | 阶段 4 | 不变（编号在 v2.1 中仍为阶段 4）|

v2.1 的设计原则：**任何需要用户确认的内容都必须先成为文件，再成为消息。** 文件是锚点，消息是过程。

## 1. 审核目标

### 1.1 双目标

| 目标 | 定义 | 判断标准 |
|------|------|---------|
| **准确性** | 文档中每一条事实性断言（路径、端口、字段、API、配置、行为）都必须与当前代码一致 | 能在源码中定位到 `文件:行号` |
| **完整性** | 文档必须覆盖模块的关键行为、隐性约束、历史坑点，不允许"代码里存在但文档里缺席"的重要路径 | 新会话中的 AI 仅凭该文档即可完成典型变更任务，无需追问用户 |

完整性是 v2.0 新增的首要目标。准确性保证文档"没错"，完整性保证文档"够用"——两者都是刚性要求。

### 1.2 最终目的

提升 AI 辅助编程的效率与质量，让 `dev_docs/` 成为项目的"可信真相源"——新会话中的 AI 读完即懂、懂即可改。

### 2.2 严格排除的目录

以下目录**不在**审核范围，原因是其内容是历史记录/过程产物，而非"描述代码现状"的真相源文档：

- `dev_docs/_analysis/` — 早期生成的项目分析与审计报告
- `dev_docs/knowledge/` — 知识库/经验沉淀
- `dev_docs/plans/` — 功能与 Bug 修复开发记录
- `dev_docs/review/` — 本审核体系自身
- `dev_docs/thinking/` — 审核或设计推理过程

子代理在审核时应被明确告知：**允许读取**这些目录作为上下文辅助（例如从 `thinking/` 中找到历史决策），但**不得**修改其中的内容，也**不得**把它们列入"需要完善的目标文档"。

## 3. 执行模型总览

```
┌─────────────────────────────────────────────────────────────────────┐
│  阶段 0：准备（主会话）                                               │
│    - 确认当前工作目录为仓库根（SkillAtlas/）                          │
│    - 加载 AI_Coding_Context.md                                       │
│    - 确认代码快照（git rev-parse HEAD 记录到 _meta.md）               │
│    - 确认子代理工具可用（Claude Code 的 Agent / opencode 的 task）    │
│    - 创建本轮审核目录：dev_docs/review/rounds/<round-id>/             │
│      └ reports/ questions/ clarifications/ proposals/ _meta.md       │
│    - 追加一条启动记录到 dev_docs/review/审核进度记录.md               │
└─────────────────────────────────────────────────────────────────────┘
                             ↓
┌─────────────────────────────────────────────────────────────────────┐
│  阶段 1：Pass 1 — 并行深审（子代理，只读目标文档）                    │
│    - 主会话为每份文档派发一个子代理                                   │
│    - 子代理必须把产物写入指定路径（而非返回到主会话内存）：            │
│        · rounds/<round>/reports/<doc>.report.md                      │
│        · rounds/<round>/questions/<doc>.questions.md                 │
│    - 报告含 A 问题清单 / B 补全建议 / C 疑问 / D 代码问题 / E 证据索引│
│    - 疑问文件单独抽取 C 章节，采用"可打勾"格式                       │
│    - 子代理返回给主会话的仅是"产物路径 + 一句摘要"                    │
│    - 主会话更新 _meta.md 的文档状态表                                 │
└─────────────────────────────────────────────────────────────────────┘
                             ↓
┌─────────────────────────────────────────────────────────────────────┐
│  阶段 1.5：疑问汇集与去重（主会话）                                   │
│    - 主会话读取 rounds/<round>/questions/*.md                        │
│    - 按模块/话题分组，识别跨文档的同质疑问                            │
│    - 生成 rounds/<round>/questions/_merged.questions.md              │
│      （合并视图 + 原始文件反向链接）                                  │
│    - 更新 _meta.md：把每条疑问标记为"待用户回答"                      │
└─────────────────────────────────────────────────────────────────────┘
                             ↓
┌─────────────────────────────────────────────────────────────────────┐
│  阶段 2：用户逐条确认（用户）                                         │
│    - 用户在 IDE 直接打开 _merged.questions.md 或各 *.questions.md    │
│    - 按条回答："为什么"类问题由用户讲清意图                           │
│    - 用户把答案写入对应的                                             │
│      rounds/<round>/clarifications/<doc>.answers.md                  │
│    - 每条疑问有三态：已回答 / 待后续 / 不确定                         │
│    - 用户可分多回合，不必一次完成                                     │
│    - 主会话负责检查答复完整性（所有必答疑问都已关闭）                 │
└─────────────────────────────────────────────────────────────────────┘
                             ↓
┌─────────────────────────────────────────────────────────────────────┐
│  阶段 2.5：推荐修复方案评估（方案子代理 + 用户批准）                  │
│    - 主会话为每份"报告 + 答复已就绪"的文档派发一个"方案子代理"        │
│    - 方案子代理读取：原文档 + report.md + answers.md                 │
│    - 输出 rounds/<round>/proposals/<doc>.proposal.md：               │
│        · 按 Pass 1 每条问题给出"前/后"对比或 patch 预览               │
│        · 明确：采纳 / 因缺证据放弃 / 延后                             │
│        · 综合评估：改动规模、风险点、是否建议采纳                     │
│    - 用户 review proposal，可就地打勾/划掉/补注                      │
│    - 用户显式批准（在 _meta.md 中标记"方案已批准"）后才能进入阶段 3   │
└─────────────────────────────────────────────────────────────────────┘
                             ↓
┌─────────────────────────────────────────────────────────────────────┐
│  阶段 3：Pass 2 — 并行重写（子代理，可写目标文档）                    │
│    - 主会话为每份已批准方案的文档派发一个子代理                       │
│    - 子代理的唯一修改指令源是 proposal.md，不得偏离                  │
│    - 若执行中发现 proposal 与代码冲突，必须停下并在                   │
│      _meta.md 中记录异常，等待用户裁定                                │
│    - 子代理只能修改指定的目标文档                                     │
└─────────────────────────────────────────────────────────────────────┘
                             ↓
┌─────────────────────────────────────────────────────────────────────┐
│  阶段 4：跨文档一致性检查（主会话）                                   │
│    - 主会话作为"编辑总控"，读取全部已重写的文档                       │
│    - 检查端口、路径、术语、字段名、服务名是否跨文档统一               │
│    - 不一致清单写入 rounds/<round>/consistency_check.md               │
│    - 发现冲突时派发定向修复子代理或主会话直接修订                     │
└─────────────────────────────────────────────────────────────────────┘
                             ↓
┌─────────────────────────────────────────────────────────────────────┐
│  阶段 5：沉淀副产物（主会话）                                         │
│    - 推理过程归档到 dev_docs/thinking/<date>_<topic>.md               │
│    - 代码问题归档到 dev_docs/plans/bugfixes/<date>_<slug>.md          │
│    - 更新 dev_docs/review/审核进度记录.md                             │
│    - 更新 AI_Coding_Context.md 的交叉引用（如有变化）                 │
│    - 本轮 rounds/<round>/ 目录本身作为中间产物归档保留               │
└─────────────────────────────────────────────────────────────────────┘
                             ↓
┌─────────────────────────────────────────────────────────────────────┐
│  阶段 6：用户 Review 与合并（用户）                                   │
│    - 用户查看 diff，确认无误后合并到工作分支                          │
│    - 禁止子代理或主会话自行 git commit/push                           │
└─────────────────────────────────────────────────────────────────────┘
```

阶段 1.5 和 2.5 是 v2.1 的核心新增：前者把"报告 → 疑问"与"用户答复"解耦，让疑问可聚合可去重；后者把"方案预览"作为 Pass 2 的前置门禁，用户在重写之前就能刹车。

## 4. 子代理使用规范

### 4.1 为什么必须使用子代理

方式一 v1.0 的核心缺陷是"单会话审 21 份文档"导致的注意力衰减。子代理给每份文档独立上下文窗口，从结构上解决该问题，并允许并行执行。在 Claude Code 中使用 `Agent` 工具（建议 `subagent_type: general-purpose` 或 `Explore`），在 opencode 中使用其对应的 task/subagent 能力。

### 4.2 子代理必须遵循的约束

| 约束 | 说明 |
|------|------|
| **隔离性** | 每个子代理只处理一份目标文档，不得同时修改多份 |
| **产物路径受控** | 子代理的产物必须写入主会话预先注入的轮次目录路径；不得自行决定写入位置 |
| **Pass 1 只读目标文档** | 阶段 1 子代理只能 Read 目标文档与源码，写入限于 `rounds/<round>/reports/` 和 `questions/` |
| **Pass 2 只改目标文档** | 阶段 3 子代理只能修改主会话指定的目标 `dev_docs/*.md`，且修改指令源仅限该文档对应的 `proposal.md` |
| **跨文件禁写** | 子代理不得写入任何不在"分配清单"中的文件 |
| **禁止修改代码** | 子代理不得修改 `Services/` 或任何非文档文件 |
| **禁止合并** | 子代理不得执行 `git add/commit/push` |
| **产出可审阅** | 子代理返回时只给"产物路径 + 一句摘要 + 异常（若有）"，报告正文放在磁盘文件中 |
| **必须声明不确定** | 任何无法从代码中直接验证的断言，必须写入 `questions/<doc>.questions.md` 而不是凭直觉填写 |
| **Pass 2 不得偏离方案** | 阶段 3 子代理若发现 proposal 与实际代码冲突，必须停下并在 `_meta.md` 的异常区写一条，等待用户裁定 |

### 4.3 并行度建议

- 同时派发的子代理数量建议 **≤4**，避免本地资源与 API 速率争用
- L1 层文档（3 份）**单独一批**先做，确保入口一致后再处理 L2/L3
- L2（4 份）可一次批量派发
- L3（6 份）分两批派发

### 4.4 子代理 vs 主会话的职责划分

| 任务 | 负责方 | 理由 |
|------|--------|------|
| 单文档深审 / 重写 | 子代理 | 上下文隔离 |
| 跨文档一致性 | 主会话 | 子代理各自只看一份文档 |
| 用户交互 / 澄清收集 | 主会话 | 子代理无法实时对话 |
| 副产物归档 | 主会话 | 避免多个子代理同时写 `thinking/` |
| 进度记录更新 | 主会话 | 单点写入，避免冲突 |
| 合并到分支 | 用户 | 禁止自动化 |

### 4.5 断点续审机制

v2.1 把中间产物全部物化到 `rounds/<round>/` 目录，断点续审从"凭进度记录字符串恢复"升级为"凭目录文件恢复"。每份文档在 `rounds/<round>/_meta.md` 的文档状态表中维护以下状态：

| 状态 | 判定依据（文件存在性）| 含义 |
|------|----------------------|------|
| `未开始` | 无 `reports/<doc>.report.md` | 本轮未派发 Pass 1 |
| `Pass1进行中` | 无报告文件，但已记录派发时间 | 子代理在跑 |
| `Pass1已完成` | 存在 `reports/<doc>.report.md` + `questions/<doc>.questions.md` | 等待阶段 1.5 |
| `疑问待用户回答` | 存在 `questions/<doc>.questions.md` 但 `clarifications/<doc>.answers.md` 不存在或含 `[ ]` 未勾选条目 | 等待用户 |
| `方案生成中` | 答复已就绪，已派发方案子代理 | 等待 proposal |
| `方案待用户批准` | 存在 `proposals/<doc>.proposal.md`，`_meta.md` 中未标注 `approved` | 等待用户 |
| `Pass2进行中` | 方案已批准，已派发 Pass 2 子代理 | 子代理在改文档 |
| `已完成` | 目标文档已重写，且跨文档检查通过 | 终态 |
| `已延后` | `_meta.md` 显式标注 | 本轮跳过，原因需记录 |
| `异常` | `_meta.md` 异常区有条目 | 阶段 3 中发现 proposal 与代码冲突，需用户裁定 |

中断后重新开始审核时，主会话只需执行以下三步即可恢复：

1. 读取 `_meta.md` 获取本轮元信息与异常区
2. 扫描 `rounds/<round>/` 下的 reports/questions/clarifications/proposals 文件
3. 根据上表反推每份文档的状态，从最早的非终态位置续做

这个机制下，即使主会话完全换到一个新会话，审核也可以无损续做。`已完成` 的文档在下一轮基线全审前不需要重做。

## 5. Prompt 模板

### 5.1 Pass 1 深审 prompt（派发给子代理）

```
你是 SkillAtlas 项目的一名资深文档审核员。请对一份开发文档进行 **只读模式**
的深度审核，目标是让这份文档成为"AI 辅助编程时的可信真相源"。

【项目上下文】
你必须首先 Read dev_docs/AI_Coding_Context.md 作为项目全景 primer。

【本轮审核目录（由主会话注入）】
ROUND_DIR = dev_docs/review/rounds/<round-id>/
REPORT_PATH    = ROUND_DIR/reports/<doc-basename>.report.md
QUESTIONS_PATH = ROUND_DIR/questions/<doc-basename>.questions.md

【目标文档】
TARGET_DOC = <此处填入目标文档完整路径，例如 dev_docs/kafka_event_system.md>

【审核目标】
1) 准确性：文档中每一条事实性断言（路径、端口、字段、API、配置、行为）
   必须能在源码中定位到具体的"文件:行号"；
2) 完整性：文档必须覆盖该模块的关键行为、隐性约束与历史坑点。判断完整性
   的唯一标准是——一个新会话的 AI 仅凭这份文档能否完成一次典型变更任务。

【硬性约束】
- 本次为只读审核：不得修改 TARGET_DOC，不得修改任何代码；
- 严禁修改 Services/ 下的任何文件；
- 除了 REPORT_PATH 和 QUESTIONS_PATH 两个产物文件，不得写入任何其他文件；
- 允许读取 dev_docs/plans/bugfixes/ 与 dev_docs/thinking/ 作为上下文辅助；
- 不得把 dev_docs/_analysis / knowledge / plans / review / thinking 列为
  "目标文档"——它们不在审核范围内；
- 任何无法在代码中直接验证的断言，必须写入 QUESTIONS_PATH 而不是凭直觉填写；
- 你返回给调用方的消息**只能包含**：产物文件路径 + 一句话摘要 + 异常（如有）。
  报告正文**必须**写到 REPORT_PATH，疑问**必须**写到 QUESTIONS_PATH。

【REPORT_PATH 文件结构】（使用 Write 工具写入）

---
doc: <TARGET_DOC>
round: <round-id>
reviewer: pass1-subagent
git_head: <由主会话注入>
written_at: <今日 ISO 日期>
```

## 6. 审核检查维度

本章节同时承担两个作用：(a) 作为子代理 Pass 1 审核时的维度参考；(b) 作为 v1.0 检查清单的详细化沉淀，保证细粒度要点无遗漏。

### 6.1 维度优先级矩阵

| 维度 | 验证点 | 优先级 |
|------|--------|--------|
| 准确性 | API 路径、端口号、配置参数是否正确 | **P0** |
| 准确性 | 数据模型、表结构、字段类型是否匹配 | **P0** |
| 准确性 | 代码示例是否来自真实代码（含行号） | **P0** |
| 完整性 | 所有核心服务与模块是否有文档覆盖 | **P0** |
| 完整性 | 关键业务流程是否被端到端描述 | **P0** |
| 完整性 | 启动依赖 / 健康检查 / 容错策略是否记录 | P1 |
| 完整性 | 历史坑点是否引用到 `plans/bugfixes/` | P1 |
| 一致性 | 服务名、端口、技术栈描述跨文档统一 | P1 |
| 一致性 | 术语使用统一（如 sa_id vs skill_id） | P1 |
| 时效性 | `verified_at` 在 3 个月以内 | P2 |
| 时效性 | 新功能是否已反映到文档 | P2 |

v2.0 将"完整性"相关项从 v1.0 的 P1 提升到 P0，与"准确性"并列。

### 6.2 文档基本信息（每份文档必检）

- [ ] 文档标题与内容一致
- [ ] 元数据（`title` / `summary` / `keywords` / `scope`）准确
- [ ] `verified_at` 不超过 3 个月
- [ ] `related_files` 指向的文件确实存在
- [ ] `dependencies` 引用的文档确实存在

### 6.3 代码验证项（子代理的核心工作）

- [ ] 文档中提及的文件路径真实存在
- [ ] 代码示例的文件路径与行号正确
- [ ] 代码示例与实际代码逐字一致（包括缩进）
- [ ] API 路径与 `routes/` 下的定义一致
- [ ] 端口号与 `docker-compose.yaml` 一致
- [ ] 配置参数与 `.env` / `config.py` 一致
- [ ] 数据库字段名、类型、约束与 `models.py` 一致
- [ ] 环境变量名与实际使用一致

### 6.4 内容质量项

- [ ] 术语使用统一
- [ ] 示例完整、可运行
- [ ] 文档内部链接和外部链接可访问
- [ ] 无明显拼写或语法错误
- [ ] Mermaid 图表语法正确
- [ ] 代码块语言标识正确

### 6.5 跨文档一致性项（由主会话阶段 4 统一检查）

- [ ] 服务名与 `service_topology.md` 一致
- [ ] 数据模型与 `database_schema.md` 一致
- [ ] 端口号在各文档中完全一致
- [ ] 技术栈描述统一
- [ ] API 路径在各文档中一致

### 6.6 特殊检查项

- [ ] TODO / 待完成内容有明确标注
- [ ] 已删除或已废弃的功能在文档中同步清理
- [ ] 与代码注释的同步性（注释过时按"代码问题"归档）
- [ ] 空章节或占位内容标记清晰

### 6.7 常见问题模式速查

子代理可参照以下 8 种历史高频模式快速扫描文档：

| # | 模式 | 典型验证方法 |
|---|------|-------------|
| 1 | 文件路径错误 | Glob 验证路径存在 |
| 2 | 行号不匹配 | Read 读取实际代码 |
| 3 | 端口号错误 | 检查 `docker-compose.yaml` 与服务 `config.py` |
| 4 | API 路径不一致 | Grep `@router` / `@app.route` 装饰器 |
| 5 | 数据模型不一致 | 读取对应服务的 `models.py` 逐字段比对 |
| 6 | 配置项缺失 | 对比 `.env.example` 与配置文件 |
| 7 | 术语混用 | 全局 Grep 术语（如 `sa_id` vs `skill_id`） |
| 8 | 链接失效 | 检查目标文件是否存在；外链尝试访问 |

## 7. 定期重审机制

文档体系必须周期化维护，否则会随代码演进迅速腐化。建议的触发条件：

### 7.1 时间触发
- **每季度一次**基线全量审核（13 份文档全部跑一遍 Pass 1+2）
- **每月一次**抽样审核（随机抽 3 份 L2/L3 做 Pass 1）

### 7.2 事件触发
在下列事件发生时，**必须**对相关文档做定向审核（至少 Pass 1）：

| 触发事件 | 必须重审的文档 |
|---------|----------------|
| 新增 / 删除微服务 | `service_topology.md`, `AI_Coding_Context.md`, `api_gateway.md` |
| 修改 `docker-compose.yaml` | `service_topology.md`, `deployment_guide.md`, `kafka_event_system.md` |
| 修改 `Services/*/app/models.py` | `database_schema.md` + 对应服务文档 |
| 新增 / 修改 Kafka topic 或事件 | `kafka_event_system.md`, `inter_service_communication.md` |
| 修改 API 路由 | `api_gateway.md` + 对应服务文档 |
| 新增 / 修改查询协议 | `query_engine_design.md` |

### 7.3 手动触发
- 重要版本发布前
- AI 辅助编程中反复出现"文档与代码不符"的投诉时
- 新成员 onboard 遇到文档歧义时

### 7.4 触发记录
所有重审事件都记录在 `dev_docs/review/审核进度记录.md` 的"重审日志"章节，便于追溯。

## 8. 退出条件

一轮完整审核（Pass 1 → 阶段 1.5 合并 → 阶段 2 澄清 → 阶段 2.5 方案 → Pass 2 → 跨文档一致性）完成后，必须同时满足：

- [ ] 本轮 `rounds/<round-id>/` 目录结构完整，`_meta.md` 已写入启动元信息
- [ ] 13 份目标文档全部在 `reports/` 下有对应的 `*.report.md`
- [ ] 13 份目标文档全部在 `questions/` 下有对应的 `*.questions.md`
- [ ] `_merged.questions.md` 已生成并覆盖全部原始疑问
- [ ] 所有原始 `*.questions.md` 与 `_merged.questions.md` 中的必答条目已在 `clarifications/` 下获得答复（无遗留 `[ ]`），或已显式标注"待后续"/"不确定"
- [ ] 每份需修订的文档在 `proposals/` 下有对应的 `*.proposal.md`，且已被用户在 `_meta.md` 中显式批准
- [ ] 所有 Pass 2 的阶段 3 子代理均以"正常完成"或"异常已裁定"收尾，`_meta.md` 异常区为空或均标注已处理
- [ ] `consistency_check.md` 已生成且所有冲突均已修复
- [ ] 所有"代码问题观察"都已归档到 `plans/bugfixes/` 并在相关文档中交叉引用
- [ ] 每份目标文档的 `verified_at` 已更新为审核当日日期
- [ ] `审核进度记录.md` 已追加本次审核摘要与指向 `rounds/<round-id>/` 的链接
- [ ] **终极验收**：用户（或另开一个空白 Claude Code 会话）随机抽取 1 份文档，让 AI 仅凭它完成一次典型变更任务，AI 不追问即可完成

最后一条是唯一真正重要的验收条件。其他都是过程指标。

## 11. 迭代优化

本审核计划本身也是一份会腐化的文档。执行过程中如果发现以下任一情况，应随时调整本计划并在 `审核进度记录.md` 中留痕：

- 某一层的文档数量或分层不再反映项目现状（例如新增微服务文档）
- 某个 prompt 模板产出的报告质量不稳定
- 某个检查维度长期无问题，可以降优先级
- 触发条件不足或过度（例如某类代码变更未命中触发表）
- 子代理的并行度、工具选择等最佳实践随 CLI 版本更新而变化

修订原则：**小步修订、必须升版本号**（v2.0 → v2.1 ...），并在 §0 版本变更说明中追加一行差异描述，避免出现无法追溯的暗改。

## 12. 审核产物目录结构

v2.1 把审核过程的中间产物全部物化到磁盘，核心思想是：**任何需要用户确认的内容都必须先成为文件，再成为消息**。本章说明目录与文件约定，以及 `审核进度记录.md` 与轮次目录的关系。
