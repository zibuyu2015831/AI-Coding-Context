# 文档审核核心原则说明

> **版本**: v2.0
> **修订时间**: 2026-04-10
> **重要性**: ⭐⭐⭐⭐⭐ 最高优先级
> **配套文档**: `审核计划.md` v2.0

---

## 0. v2.0 修订说明

v1.0 的核心原则是"只审核文档、不修改代码"——它在"准确性"维度上非常有效，但过度收敛的副作用是**失去补全动力**。v2.0 在保留安全底线的同时，把审核目标从单一的"准确性"扩展为"准确性 + 完整性"，并把"发现的代码问题"的处理方式从"仅观察"升级为"**必须记录**到 `plans/bugfixes/`"。

---

## 1. 审核目标

**唯一最终目的**：让 `dev_docs/` 成为 SkillAtlas 项目的"可信真相源"，使 AI 辅助编程的效率和质量得到实质性提升。

实现这一目的必须同时达成两个子目标：

| 子目标 | 定义 | 验收标准 |
|--------|------|---------|
| **准确性** | 每一条事实性断言必须与代码一致 | 能定位到 `文件:行号` |
| **完整性** | 文档必须覆盖模块的关键行为与隐性约束 | 新会话的 AI 仅凭这份文档能完成典型变更任务而无需追问 |

v1.0 只要求前者，v2.0 要求两者同时满足。完整性是本版的新增硬性要求。

---

## 2. 五条核心原则

### 原则 1 — 代码是唯一真相源

文档是代码的索引，不是代码的替代。当文档与代码不一致时：

| 情形 | 正确做法 | 错误做法 |
|------|---------|---------|
| 文档的 API 路径是 `/api/v1/skills/`，代码是 `/api/v1/registry/skills/` | ✅ 修改文档以匹配代码 | ❌ 修改代码以匹配文档 |
| 文档说功能已实现，代码未实现 | ✅ 标注"规划中，未实现"或删除该段 | ❌ 立刻实现以匹配文档 |
| 文档描述的行为与代码的实际行为有偏差 | ✅ 以代码为准重写描述 | ❌ 假装代码就是文档说的那样 |

每一条经过审核的断言都必须带有源码证据（`文件:行号`），无证据即不写。

### 原则 2 — 双目标，不可偏废

**审核 = 准确性验证 + 完整性补全**。两者缺一不可。

- 只做准确性 → 文档"没错但没用"，AI 读完仍要追问用户
- 只做完整性 → 文档越写越厚但充斥猜测，AI 被错误信息误导
- 同时做两者 → 文档"没错且够用"，AI 读完即可工作

完整性的具体体现（子代理在重写时应主动补充）：

- 模块的关键路径是否完整可追（请求进入 → 校验 → 持久化 → 事件 → 对外返回）
- 启动依赖、健康检查、容错策略
- 并发 / 重试 / 幂等 / 错误码 / 边界条件
- 历史坑点（通过引用 `dev_docs/plans/bugfixes/` 实现）

### 原则 3 — 代码问题必须记录（不是"仅观察"）

v1.0 要求"发现代码问题只观察不修复"，v2.0 在此基础上**加强**：**必须**把代码问题结构化归档到 `dev_docs/plans/bugfixes/<date>_<slug>.md`，并在相关文档中交叉引用。

这样做的原因是：dev-zibuyu 分支的实践证明，"文档审核时发现的代码问题"是项目质量的高价值副产物，如果只观察不记录，这些发现会在会话结束后消失。

| 情形 | 正确做法 |
|------|---------|
| 发现 Bug | ⚠️ 新建 `plans/bugfixes/<date>_<slug>.md`，记录现象、位置、影响 |
| 发现配置不一致 | ⚠️ 同上，并在文档中以"参见 BUG-N"形式交叉引用 |
| 发现注释过时 | ⚠️ 同上（归类为"文档-代码同步"问题） |
| 发现设计缺陷 | ⚠️ 同上，并在备注中注明"本次审核不做重构决策" |

**仍然禁止**：审核过程中直接修改 `Services/` 下的任何代码文件。记录是为了后续统一排期修复，不是为了就地动手。

### 原则 4 — 子代理隔离 + 两遍协作

当使用 Claude Code / opencode 执行审核时，必须采用"主会话编排 + 并行子代理"模型（详见 `审核计划.md` §3）：

- **子代理**：每份文档一个子代理，独立上下文窗口，只做一份文档的深审或重写
- **主会话**：编排、汇总、与用户交互、跨文档一致性检查、副产物归档
- **两遍协议**：Pass 1 只读深审 → 主会话收集疑问 → 用户澄清 → Pass 2 可写重写

这一机制是 v2.0 区别于 v1.0 的结构性核心。禁止把 13 份文档塞进同一个会话串行审核。

### 原则 5 — 验收标准是"AI 新会话可用"

文档审核是否完成，唯一的终极标准是：

> 在一个全新的 Claude Code 会话中，随机抽取一份被审过的文档，让 AI 仅凭这份文档（加上 `AI_Coding_Context.md`）完成一次典型变更任务——AI 若能在不追问用户的情况下完成，则该文档验收通过。

其他过程指标（问题清单勾完、`verified_at` 更新等）都只是必要条件，不是充分条件。

## 3. 审核范围边界

### 3.1 在审范围（13 份，`dev_docs/` 顶层）

参见 `审核计划.md` §2.1 的 13 份文档表。这些文档是"描述代码现状"的真相源。

### 3.2 严格排除的目录

以下 5 个子目录**不在**审核范围，也不得被子代理当作"需要完善的目标文档"：

| 目录 | 性质 | 可否读取 | 可否修改 |
|------|------|---------|---------|
| `dev_docs/_analysis/` | 历史分析报告 | ✅（辅助） | ❌ |
| `dev_docs/knowledge/` | 经验知识库 | ✅（辅助） | ❌ |
| `dev_docs/plans/` | 开发与 Bug 修复记录 | ✅（辅助） | ⚠️ 仅允许**追加**新的 bugfix 记录，不得修改已有内容 |
| `dev_docs/review/` | 审核体系自身 | ✅（辅助） | ⚠️ 仅允许在 `审核进度记录.md` 中追加进度 |
| `dev_docs/thinking/` | 推理过程归档 | ✅（辅助） | ⚠️ 仅允许追加新的推理归档 |

排除的原因：这 5 个目录的内容是**过程产物或历史快照**，不以"反映当前代码现状"为目标。审核它们没有意义，修改它们会破坏项目的过程记录。

### 3.3 可"读而不改"的引用关系

子代理在深审或重写目标文档时，**必须**允许自己从 `plans/bugfixes/` 与 `thinking/` 中汲取上下文——那里藏着很多"代码看不出来的为什么"。但这些引用只能以链接形式出现在目标文档中，不得直接把整段内容复制过来。

## 4. 问题分类与处理矩阵

| 问题类型 | 示例 | 处理方式 | 归档位置 |
|---------|------|---------|---------|
| 文档准确性问题 | 端口号错误、API 路径错误 | ✅ 修改文档 | 进度记录 + 文档本身 |
| 文档完整性问题 | 关键流程缺失、错误路径未描述 | ✅ 补全文档 | 进度记录 + 文档本身 |
| 文档一致性问题 | 术语不统一、跨文档矛盾 | ✅ 统一并修改文档 | 跨文档一致性检查报告 |
| 文档时效性问题 | `verified_at` 过期 | ✅ 更新元数据 | 文档 front matter |
| 代码 Bug | 逻辑错误、异常未处理 | ⚠️ 记录到 `plans/bugfixes/` | `dev_docs/plans/bugfixes/` |
| 代码设计缺陷 | 架构不合理 | ⚠️ 同上 | 同上 |
| 代码注释过时 | 注释描述与实际行为不符 | ⚠️ 同上（归类为"文档-代码同步"）| 同上 |

## 5. 疑问与澄清的处理流程

子代理不能实时与用户对话，所以 v2.0 采用"集中式澄清"：

1. **Pass 1 中**：子代理遇到任何无法从代码直接验证的设计意图、历史决策或歧义，**必须**把它写入报告的"C. 需要用户澄清的疑问"章节，而不是凭直觉猜测。
2. **Pass 1 后**：主会话汇总所有子代理的疑问，按文档分组呈现给用户。
3. **用户回答**：用户批量回答，重点讲"为什么"而不是"是什么"（"是什么"可以从代码读出来）。
4. **Pass 2 前**：主会话把澄清整理成结构化的"澄清包"，作为 Pass 2 子代理的输入。

未经澄清的疑问**不允许**在 Pass 2 中凭假设写入文档。如果用户暂时无法回答，应标记为 `TODO: 待澄清`，在文档中保留问题本身而不是编造答案。

## 6. 禁止事项 vs 坚持事项

### ⚠️ 绝对禁止

1. 借审核之名直接修改 `Services/` 下的任何代码
2. 把 `_analysis/`、`knowledge/`、`plans/`、`review/`、`thinking/` 当作审核目标
3. 把 13 份文档塞进同一个会话串行审核（必须用子代理）
4. 凭直觉填写未经源码验证的断言
5. 子代理擅自跨文档写入
6. 子代理或主会话自动 `git commit / push`
7. 删除 `plans/bugfixes/` 或 `thinking/` 中已有的记录

### ✅ 必须坚持

1. 代码是唯一真相源，文档向代码对齐
2. 准确性 + 完整性双目标缺一不可
3. 代码问题必须**记录**（不是仅观察）
4. 子代理隔离 + 两遍协议
5. 终极验收 = AI 新会话仅凭单份文档可完成典型任务
6. 所有修改必须经过用户 review 后才进入分支
7. 每次审核都更新 `verified_at` 与进度记录

## 7. 周期化维护原则

文档体系不是一次性成果，而是"活"的资产。长期保持准确与完整，必须依赖以下机制：

1. **季度全审**：每季度做一次完整的 13 份文档 Pass 1+2
2. **月度抽审**：每月抽 3 份做 Pass 1，验证文档腐化速度
3. **事件触发审核**：在关键代码变更时强制触发（详见 `审核计划.md` §7.2 的触发条件表）
4. **任何"AI 投诉"即重审**：当 AI 辅助编程中多次抱怨"文档与代码不符"时，立刻对相关文档发起定向 Pass 1
5. **审核动作本身留痕**：所有审核事件归档到 `审核进度记录.md`，包括所用的代码快照（`git rev-parse HEAD`），便于追溯

周期化是本原则文档的一部分，不是可选项。没有周期化的文档体系一定会腐化。

## 8. 成功标准

本审核体系运行良好的表现：

- ✅ 13 份文档的 `verified_at` 均在 3 个月以内
- ✅ `plans/bugfixes/` 持续沉淀新的发现，且被主文档交叉引用
- ✅ `thinking/` 持续沉淀深审推理过程
- ✅ 新成员或 AI 在 onboard 时几乎不向用户追问"这段代码为什么是这样"
- ✅ AI 辅助编程中因"文档错误"导致的错误建议次数趋近于零
- ✅ 每次全审完成后，随机抽审的"AI 新会话可用"测试通过率 ≥ 12/13

## 9. 执行前的自我确认清单

每次发起审核前，执行人（人或主会话）应对自己确认：

- [ ] 我理解本次审核追求准确性 + 完整性双目标
- [ ] 我理解审核范围严格排除 `_analysis/knowledge/plans/review/thinking/` 五个子目录
- [ ] 我会通过子代理（Agent 工具）为每份目标文档分配独立上下文
- [ ] 我会采用"Pass 1 只读 → 澄清 → Pass 2 重写"两遍协议
- [ ] 我理解子代理不得修改代码、不得跨文档写入、不得自动 commit
- [ ] 我理解发现代码问题必须记录到 `plans/bugfixes/`，而不是仅观察
- [ ] 我会在完成后更新 `verified_at` 并追加 `审核进度记录.md`
- [ ] 我会把合并到分支的最终决定留给用户
