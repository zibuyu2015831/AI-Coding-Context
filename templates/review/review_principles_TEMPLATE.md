## 1. 审核的唯一最终目的

让 `dev_docs/` 成为 **{PROJECT_NAME}** 项目的 **"可信真相源"**。

> **检验标准**：在一个全新的会话中，AI 仅凭被审文档（加上 `AI_Coding_Context.md`）
> 能够完成一次典型的开发变更任务，而无需追问用户任何问题。

实现这一目的，必须同时满足两个子目标：

| 子目标 | 定义 | 验收标准 |
|--------|------|---------|
| **准确性** | 每一条事实性断言必须与当前代码一致 | 能在源码中定位到 `文件:行号` |
| **完整性** | 文档必须覆盖模块的关键行为、隐性约束与历史坑点 | 新会话 AI 仅凭此文档能完成典型变更任务，无需追问 |

两者缺一不可：
- 只做准确性 → 文档"没错但没用"，AI 读完仍要追问用户
- 只做完整性 → 文档越写越厚但充斥猜测，AI 被错误信息误导
- 同时做两者 → 文档"没错且够用"，AI 读完即可工作

## 2. 五条核心原则

### 原则 1：代码是唯一真相源

文档是代码的索引，不是代码的替代。当文档与代码不一致时：

| 情形 | 正确做法 ✅ | 错误做法 ❌ |
|------|-----------|-----------|
| 文档 API 路径与代码不符 | 修改文档以匹配代码 | 修改代码以匹配文档 |
| 文档说功能已实现，代码未实现 | 标注"规划中，未实现"或删除该段 | 立刻实现以匹配文档 |
| 文档描述的行为与代码实际行为有偏差 | 以代码为准重写描述 | 假装代码就是文档说的那样 |

每一条经过审核的断言都必须带有源码证据（`文件:行号`），无证据即不写。

### 原则 2：双目标，不可偏废

**审核 = 准确性验证 + 完整性补全**。

完整性的具体体现（子代理在生成修复计划时应主动补充）：
- 模块的关键路径是否完整可追（请求进入 → 校验 → 持久化 → 对外返回）
- 启动依赖、健康检查、容错策略
- 并发 / 重试 / 幂等 / 错误码 / 边界条件
- 历史坑点（通过引用 `dev_docs/plans/bugfixes/` 实现）

### 原则 3：代码问题必须记录（不仅是观察）

审核过程中发现的代码问题，必须结构化归档到 `dev_docs/plans/bugfixes/<date>_<slug>.md`，并在相关文档中交叉引用。

> 原因：文档审核时发现的代码问题是项目质量的高价值副产物。如果只观察不记录，这些发现会在会话结束后消失。

| 情形 | 正确做法 |
|------|---------|
| 发现 Bug | ⚠️ 新建 `plans/bugfixes/<date>_<slug>.md`，记录现象、位置、影响 |
| 发现配置不一致 | ⚠️ 同上，并在文档中以"参见 BUG-N"形式交叉引用 |
| 发现注释过时 | ⚠️ 同上（归类为"文档-代码同步"问题） |
| 发现设计缺陷 | ⚠️ 同上，备注"本次审核不做重构决策" |

**仍然禁止**：审核过程中直接修改任何代码文件。

### 原则 4：子代理隔离 + 多阶段协议

执行审核时，必须采用"主会话编排 + 并行子代理"模型（详见 `sys_review_plan.md`）：

- **深审子代理**：每份文档独立上下文，只做一份文档的深审（阶段 1）
- **计划子代理**：每份文档独立上下文，生成该文档的修复计划（阶段 3a）
- **执行子代理**：每份文档独立上下文，按修复计划执行改动（阶段 3c）
- **主会话**：编排、汇总、与用户交互、跨文档一致性审查、副产物归档

禁止把所有文档塞进同一个会话串行处理——这会导致注意力衰减，后期文档的审核质量无法保证。

### 原则 5：终极验收标准是"AI 新会话可用"

文档审核是否完成，唯一的终极标准：

> 在一个全新的会话中，随机抽取一份被审过的文档，
> 让 AI 仅凭这份文档（加上 `AI_Coding_Context.md`）完成一次典型变更任务——
> AI 若能在不追问用户的情况下完成，则该文档验收通过。

其他过程指标（问题清单勾完、`verified_at` 更新等）都只是必要条件，不是充分条件。

## 4. 问题分类与处理矩阵

| 问题类型 | 示例 | 处理方式 | 归档位置 |
|---------|------|---------|---------|
| 文档准确性问题 | 端口号错误、API 路径错误 | ✅ 修改文档（通过 fix_plan → 执行子代理）| 文档本身 |
| 文档完整性问题 | 关键流程缺失、容错策略未描述 | ✅ 补全文档（通过 fix_plan → 执行子代理）| 文档本身 |
| 文档一致性问题 | 术语不统一、跨文档矛盾 | ✅ 在裁定快照中统一裁定后修复 | `_round_decisions.md` + 文档本身 |
| 文档时效性问题 | `verified_at` 超过 3 个月 | ✅ 更新元数据 | 文档 front matter |
| 代码 Bug | 逻辑错误、异常未处理 | ⚠️ 记录到 `plans/bugfixes/`（不修复代码）| `plans/bugfixes/` |
| 代码设计缺陷 | 架构不合理 | ⚠️ 同上 | 同上 |
| 代码注释过时 | 注释与实际行为不符 | ⚠️ 同上（归类为"文档-代码同步"）| 同上 |

## 5. 绝对禁止 vs 必须坚持

### ⚠️ 绝对禁止

1. 直接修改任何代码文件（`{SRC_DIR}/` 等）
2. 把 `_analysis/`、`knowledge/`、`plans/`、`review/`、`thinking/` 当作审核目标
3. 把多份文档塞进同一个会话串行处理（必须用子代理隔离）
4. 凭直觉填写未经源码验证的事实性断言
5. 子代理擅自跨文档写入（只能写主会话分配给它的目标文件）
6. 子代理或主会话自动执行 `git commit / push`
7. 删除 `plans/bugfixes/` 或 `thinking/` 中已有的记录

### ✅ 必须坚持

1. 代码是唯一真相源，文档向代码对齐
2. 准确性 + 完整性双目标，缺一不可
3. 代码问题必须**记录**（不是仅观察）到 `plans/bugfixes/`
4. 子代理隔离 + 多阶段分工协议
5. 每个关键决策节点等待用户显式批准后才能继续
6. 终极验收 = AI 新会话仅凭单份文档可完成典型任务
7. 所有修改必须经过用户 review 后才能 git commit
8. 每次审核都更新 `verified_at` 与 `REVIEW_LOG.md`

## 6. 周期化审核原则

文档体系不是一次性成果，而是"活"的资产。长期保持准确与完整，依赖以下机制：

1. **季度全审**：每季度做一次完整的审核（全部目标文档过完整流程）
2. **月度抽审**：每月随机抽 3 份文档做 Pass 1，验证文档腐化速度
3. **事件触发审核**：在关键代码变更时强制触发（见 `sys_review_plan.md` §触发机制）
4. **任何"AI 投诉"即重审**：当 AI 辅助编程中多次反映"文档与代码不符"时，立刻对相关文档发起审核
5. **审核动作留痕**：所有审核事件归档到 `REVIEW_LOG.md`，包括代码快照（`git rev-parse HEAD`）

## 7. 执行前自我确认清单

每次发起审核前，执行人（人或主会话）应确认：

- [ ] 我理解本次审核的唯一目的是让文档成为"AI 新会话可用"的可信真相源
- [ ] 我理解准确性 + 完整性双目标缺一不可
- [ ] 我理解审核范围严格排除 `_analysis/knowledge/plans/review/thinking/` 五个子目录
- [ ] 我会通过子代理为每份目标文档分配独立上下文
- [ ] 我理解子代理不得修改代码、不得跨文档写入、不得自动 commit
- [ ] 我理解发现代码问题必须记录到 `plans/bugfixes/`，而不是仅观察
- [ ] 我会在每个关键节点等待用户批准后才继续
- [ ] 我会在完成后更新 `verified_at` 并追加 `REVIEW_LOG.md`
- [ ] 合并到分支的最终决定由用户做出
