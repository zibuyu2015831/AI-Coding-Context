# AI Rules 目录说明

> **用途**: 存放项目的所有 AI 规则，采用模块化设计  
> **设计理念**: 独立管理、灵活组合、易于扩展

---

## 📁 目录结构

### core/ - 核心规范

项目的核心编码规范，优先级最高（P0-必须）

**包含内容**:

- API 调用规范
- 状态管理规范
- 命名约定
- 错误处理规范
- 组件/模块开发规范

### workflow/ - 工作流程

开发、修复、审查等工作流程规范（P0/P1）

**包含内容**:

- 新功能开发流程
- Bug 修复流程
- 代码审查规范
- 文档更新流程

### triggers/ - 触发器

告诉 AI 何时阅读文档、搜索知识库等（P1）

**包含内容**:

- 文档阅读触发条件
- 知识库搜索时机
- 方案创建时机

### constraints/ - 约束

禁止事项、必须执行的操作、最佳实践（P0/P1）

**包含内容**:

- 禁止事项
- 必须执行的操作
- 最佳实践建议

### combined/ - 组合文件

供 IDE 使用的组合 rule 文件，从独立 rule 自动生成

**包含文件**:

- `AI_RULES_FULL.md` - 完整版（所有 rule）
- `AI_RULES.md` - 标准版（**推荐**，核心+工作流+触发器）
- `AI_RULES_MINIMAL.md` - 精简版（仅核心规范）
- `.cursorrules.example` - Cursor 配置示例

---

## 🎯 使用方式

### 方式 1: 使用预组合文件（推荐）

1. **选择合适的组合版本**:

   - `AI_RULES_FULL.md` - 完整版，包含所有 rule（约 200 行）
   - `AI_RULES.md` - **标准版**，推荐使用（约 150 行）
   - `AI_RULES_MINIMAL.md` - 精简版，仅核心规范（约 80 行）

2. **复制到 IDE 配置**:

   **Cursor 用户**:

   ```bash
   # 复制标准版到.cursorrules
   cp dev_docs/rules/combined/AI_RULES.md .cursorrules
   ```

   **Windsurf 用户**:

   - 在项目设置中找到"Custom Rules"
   - 打开`dev_docs/rules/combined/AI_RULES.md`
   - 复制内容并粘贴

   **其他 IDE**:

   - 参考 IDE 文档配置项目级 AI 规则

3. ⚠️ **重要**: 复制时请**删除**文件开头的"使用说明"部分
   - 每个组合文件的开头都有`<!-- 使用说明 START -->`和`<!-- 使用说明 END -->`标记
   - 复制时删除这两个标记之间的内容

### 方式 2: 自定义组合

1. 从`core/`, `workflow/`, `triggers/`, `constraints/`选择需要的 rule
2. 按照以下顺序组合:
   ```
   core/* (核心规范)
   → workflow/* (工作流程)
   → triggers/* (触发器)
   → constraints/* (约束)
   ```
3. 删除每个文件开头的"使用说明"部分
4. 配置到 IDE

## 📐 Rule 文件格式说明

### 文件头部结构

每个独立的 rule 文件包含两部分:

```markdown
<!-- 使用说明 START -->
<!-- ⚠️ 复制到IDE时请删除此部分 -->

## 📋 Rule 使用说明

**Rule 名称**: [名称]
**类型**: Core/Workflow/Trigger/Constraint
**优先级**: P0/P1/P2
**使用层级**: [手动携带/必须携带/AI 决策]

### 使用层级说明

- **必须携带**: 此 rule 必须包含在 IDE 配置中
- **AI 决策**: AI 根据场景决定是否应用此 rule
- **手动携带**: 用户根据需要选择是否包含

### IDE 配置建议

- Cursor: [具体建议]
- Windsurf: [具体建议]

---

<!-- 使用说明 END -->

<!-- 实际Rule内容 START -->

[这部分是复制到 IDE 的实际内容]

<!-- 实际Rule内容 END -->
```

### 使用层级分类

**P0 - 必须携带**:

- 所有`core/`下的规范
- 关键工作流程
- 必须禁止的操作

**P1 - AI 决策**:

- `triggers/`下的触发器
- 可选工作流程
- 最佳实践建议

**P2 - 手动携带**:

- 特殊场景规范
- 扩展功能说明

## 🔄 更新机制

### 自动更新

当以下情况发生时，AI 会自动更新相关 rule 文件:

1. **技术栈升级** → 更新`core/`相关文件
2. **核心规范调整** → 更新对应的`core/`文件
3. **新增重要子文档** → 更新`triggers/document_reading.md`
4. **命名规范变更** → 更新`core/naming_convention.md`
5. **开发流程调整** → 更新`workflow/`相关文件

### 更新流程

1. **AI 检测触发条件**
2. **更新独立 rule 文件** - 修改`rules/`下的对应文件
3. **重新生成组合文件** - 自动更新`combined/`下的文件
4. **提醒用户**:

   ```markdown
   ⚠️ Rule 文件已更新

   **变更内容**:

   - [列出具体变更]

   **请手动更新 IDE 配置**:

   1. 查看更新后的 dev_docs/rules/combined/AI_RULES.md
   2. 删除开头的"使用说明"部分
   3. 复制到 IDE rule 配置文件
   4. 重新加载 IDE
   ```

## 💡 最佳实践

### 初次配置

1. **使用标准版** - `AI_RULES.md`（推荐）
2. **删除使用说明** - 复制时删除标记部分
3. **测试效果** - 与 AI 交互，观察 rule 是否生效
4. **按需调整** - 根据实际需要选择其他版本

### 日常维护

1. **定期检查** - 每次主文档更新后检查 rule 是否需要更新
2. **版本同步** - 保持 IDE 配置与`combined/`下的文件同步
3. **问题反馈** - 发现 rule 不合理时，修改对应的独立文件

### 团队协作

1. **统一配置** - 团队成员使用相同的组合版本
2. **版本控制 Rule 文件** - 将 IDE 配置文件加入版本控制
3. **定期同步** - 项目规范变更时统一更新

## 📝 常见问题

### Q: 为什么要分独立文件？

A: 便于独立更新、版本追踪、灵活组合

### Q: combined/下的文件如何生成？

A: AI 自动从独立 rule 文件组合生成

### Q: 可以手动修改 combined/下的文件吗？

A: 不建议，因为会被自动重新生成。应修改独立 rule 文件

### Q: 如何知道哪些 rule 是必须的？

A: 查看 rule 文件头部的"优先级"和"使用层级"说明

### Q: 复制时忘记删除使用说明会怎样？

A: IDE 会把说明也当作 rule，可能影响 AI 行为。请务必删除
