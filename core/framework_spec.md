# AI 辅助开发文档体系规范

> **版本**: v2.0 ✨ 已更新  
> **创建日期**: 2025-11-27  
> 本规范定义了一套**通用的 AI 辅助开发文档体系**，通过结构化文档帮助 AI 快速理解项目、保持开发规范、沉淀团队知识。

### 核心理念

1. **单一入口** - 一个主文档作为 AI 的快速上下文入口
2. **分层架构** - 主文档（索引+速查）→ 子文档（详细）→ 知识库（经验）
3. **方案驱动** - 强制规划先行，提升开发质量
4. **知识沉淀** - 持续积累项目经验，避免重复踩坑

## 🗂️ 标准产物路径（SSOT）

> **本节是 AICC 框架对所有"用户项目内生成产物"的单一真相源（Single Source of Truth）。**
> 任何文档（workflows / templates / guides / agents / core）若引用产物路径，**必须**与本表一致。

| 产物              | 标准路径                                          | 命名规则           | 说明                                |
| ----------------- | ------------------------------------------------- | ------------------ | ----------------------------------- |
| 主文档            | `dev_docs/AI_Coding_Context.md`                   | 驼峰式             | 用户项目的文档入口（注意大小写）    |
| AI Rules 文件     | `dev_docs/rules/combined/AI_RULES.md`             | 全大写             | IDE 规则源文件（IDE 配置文件惯例）  |
| 分析方案          | `dev_docs/_analysis/generation_plan.md`           | 小写下划线         | 生成方案（详见 generation_workflow） |
| 项目问题报告      | `dev_docs/_analysis/project_analysis_report.md`   | 小写下划线         | 项目分析问题清单                    |
| 生成进度          | `dev_docs/_analysis/generation_progress.md`       | 小写下划线         | 生成进度跟踪                        |
| 子文档（架构等）  | `dev_docs/architecture_overview.md` 等            | 小写下划线         | 详见"📖 子文档规范"                  |
| 计划目录          | `dev_docs/plans/`                                 | 小写复数           | features/ 与 bugfixes/ 子目录       |
| 知识库            | `dev_docs/knowledge/`                             | 小写单数           | troubleshooting / patterns / performance |

### 命名规范要点

1. **核心入口产物用驼峰/大写**：体现身份（`AI_Coding_Context.md`、`AI_RULES.md`）
2. **过程性产物用小写下划线**：与子文档一致（`generation_plan.md`、`api_layer.md`）
3. **目录全小写**：避免跨平台大小写歧义
4. **大小写敏感声明**：所有路径在 Linux 下严格区分大小写。AI 在生成时务必按本表大小写写入文件。

### 反例（已知冲突，请勿使用）

- ❌ `项目根/ai_rules.md`（小写 + 错位置）
- ❌ `dev_docs/AI_RULES.md`（缺 rules/combined/ 子路径）
- ❌ `ai_coding_context.md`（小写主文档）

## 🔧 plans/ 目录规范

### 用途

存放所有功能开发和Bug修复的**临时方案文档**。

### 目录结构

```

plans/
├── README.md # 方案索引与使用规范
├── features/ # 功能开发方案
│ └── YYYY-MM-DD\_功能描述.md
└── bugfixes/ # Bug 修复方案
└── YYYY-MM-DD_bug 描述.md

````

### 方案文档模板

```markdown
# [功能/Bug] 简短标题

## 📝 背景与问题描述

- 问题现象 / 功能需求
- 影响范围
- 优先级

## 🎯 解决方案

### 技术选型

- 方案对比
- 选择理由

### 实施步骤

1. 步骤1
2. 步骤2
3. 步骤3

### 影响评估

- 影响的模块/组件
- 兼容性考虑
- 性能影响

## ✅ 验证计划

- [ ] 功能测试
- [ ] 回归测试
- [ ] 性能测试

## 📚 参考资料

- 相关Issue链接
- 参考文档
````

## 📚 knowledge/ 目录规范

### 用途

沉淀项目开发中的**难题、解决方案、最佳实践和架构模式**。

### 目录结构

```
knowledge/
├── README.md               # 知识库索引
├── troubleshooting/        # 问题解决
│   └── 问题描述.md
├── patterns/               # 架构模式
│   └── 模式名称.md
└── performance/            # 性能优化
    └── 优化场景.md
```

### 知识文档模板

````markdown
# [主题] 标题

## 📝 问题描述

简述遇到的问题或需要实现的功能。

## 🔍 根本原因 / 核心需求

深入分析问题根源或需求本质。

## 💡 解决方案

### 方案概述

一句话总结解决思路。

### 技术实现

```code
// 关键代码示例
```
````

### 关键要点

- 要点 1: 为什么这样做
- 要点 2: 注意事项

## ⚠️ 注意事项

- 适用场景
- 不适用场景
- 潜在风险

## 📚 相关资源

- 官方文档链接
- 相关知识库文档
- 原始方案文档（如有）

## 📅 文档元信息

- 创建日期: YYYY-MM-DD
- 最后更新: YYYY-MM-DD
- 关联项目版本: vX.X.X

```

### 沉淀触发条件

**必须沉淀**：
- 解决了耗时 > 2小时的难题
- 发现了框架/库的非常规用法
- 总结了可复用的架构模式
- 性能优化效果显著（提升 > 30%）

**更新索引**：
每次新增知识文档后，在 `knowledge/README.md` 中更新索引。

## 🎯 AI生成文档的标准流程

### 第一阶段：项目分析（1-2小时）

1. **扫描代码库结构**
```

- 识别技术栈
- 统计项目规模
- 分析目录结构
- 识别核心模块

```

2. **识别架构特点**
```

- 状态管理方案
- API 调用模式
- 路由设计
- 特殊架构（多租户、微前端等）

```

3. **提取核心代码模式**
```

- API 调用示例
- 组件开发模板
- 状态管理用法
- 常用工具函数

````

### 第二阶段：文档生成（2-3小时）

1. **生成主文档** (`AI_Coding_Context.md`)
- 项目概览
- 目录速查
- 场景导航
- 核心代码模式

2. **生成子文档**（根据项目类型选择）
- 架构总览
- API层文档
- 状态管理文档
- 其他专项文档

3. **创建目录结构**
- plans/ 目录及README
- knowledge/ 目录及README

### 第三阶段：验证优化（1小时）

1. **人工审核**
- 检查文档完整性
- 验证代码示例正确性
- 补充遗漏内容

2. **AI自测**
- 用AI读取文档
- 模拟几个开发场景
- 验证能否快速定位信息

## 📊 文档质量标准

### 主文档质量检查清单

- [ ] 项目规模数据准确（文件数、代码量）
- [ ] 技术栈列表完整
- [ ] 关键目录速查包含核心目录
- [ ] 场景导航覆盖80%常见场景
- [ ] 核心代码模式可直接复制使用
- [ ] 业务模块映射表与实际代码一致
- [ ] AI编码禁忌包含项目特定注意事项
- [ ] 所有子文档链接有效

### 子文档质量检查清单

- [ ] 文档标题清晰
- [ ] 内容结构合理
- [ ] 代码示例完整可运行
- [ ] 包含注意事项和最佳实践
- [ ] 与实际代码保持同步

### 整体质量指标

- **覆盖率**: 核心功能文档覆盖 > 90%
- **准确率**: 代码示例准确率 > 95%
- **实用性**: AI能在3分钟内定位到80%问题的答案
- **维护性**: 代码变更后，文档更新耗时 < 30分钟

## 🔄 文档维护规范

### 日常维护

| 代码变更 | 需更新文档 | 更新时机 |
|---------|-----------|---------|
| 新增业务模块 | 主文档 + 模块开发文档 | 代码提交前 |
| 修改API接口 | API层文档 | 代码提交前 |
| 新增公共组件 | 组件库文档 | 代码提交前 |
| 修改配置项 | 架构/配置文档 | 代码提交前 |
| 解决难题 | knowledge/ 知识库 | 问题解决后 |
| 新增功能开发 | plans/ 方案文档 | 开发开始前 |

### 定期审查

- **每周**: 检查 plans/ 目录，归档已完成方案
- **每月**: 审查知识库，更新过时内容
- **每季度**: 全面审查主文档和子文档，确保与代码同步

### 版本管理

- 文档纳入Git版本控制
- 重大变更在主文档标注更新日期
- 保留重要历史版本备份

## 📝 使用示例

### 场景1: 新项目启动

```bash
# 1. 克隆此规范到新项目
cp -r ai_coding_context new_project/

# 2. 让AI分析项目生成文档
"请按照 ai_coding_context/AI_ENTRY_POINT.md
分析当前项目并生成完整文档体系"

# 3. 人工审核和优化
# 4. 删除 ai_coding_context（可选）
````

### 场景 2: 已有项目补充文档

```bash
# 1. 添加规范到项目
cp -r ai_coding_context existing_project/

# 2. 让AI审查现有文档
"参考 ai_coding_context 规范，审查并优化现有文档"

# 3. 补充缺失的文档和目录
```
