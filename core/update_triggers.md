## 🏗️ 三层架构

文档更新检测采用三层架构设计:

```
Layer 3: Commit-Guided (智能层) ← V3.0新增
  ↓ 基于
Layer 2: Update Triggers (规则层) ← 本文档
  ↓ 依赖
Layer 1: Git Diff (检测层) ← Git原生能力
```

### 层级说明

**Layer 1: Git Diff (检测层)**

- **职责**: 检测代码变更
- **能力**: 识别哪些文件发生了变化
- **局限**: 无法理解变更意图

**Layer 2: Update Triggers (规则层)**

- **职责**: 定义更新规则和优先级
- **能力**: 基于文件类型和变更范围判断是否需要更新文档
- **局限**: 需要人工解释变更内容

**Layer 3: Commit-Guided (智能层)** 🆕

- **职责**: 自动化文档更新流程
- **能力**: 解析结构化 commit 信息(WHAT/WHY/HOW),自动识别受影响文档
- **优势**: 无需人工解释,直接从 commit 提取意图

### 协作模式

**有结构化 commit 时**:

```
Commit-Guided 解析WHAT/WHY/HOW
  ↓
自动映射到 P0/P1/P2 级别
  ↓
精准定位受影响文档
  ↓
生成更新草稿
```

**无结构化 commit 时**:

```
降级到 Update Triggers 传统检测
  ↓
基于 Git Diff + 文件类型判断
  ↓
提示用户补充变更信息
```

**详细说明**: 参见 [workflows/commit_guided_update.md](../workflows/commit_guided_update.md)

## 📝 核心问题

**何时应该更新 AI 文档?**

当项目代码发生变化后,并非所有变更都需要更新文档。本规范定义了明确的触发条件。

---

## 🚀 Commit-Guided 自动触发 (V3.0 新增)

### 触发条件

当检测到以下类型的 commit 时,自动触发文档更新流程:

1. **结构化 Commit**: 包含 `prompt:` / `ai:` / `doc:` 前缀
2. **用户明确请求**: "基于最近的 commit 更新文档"
3. **Merge Commit**: 合并后扫描 source branch 的结构化提交

### 自动优先级映射

Commit-Guided 会自动将 commit 信息映射到 P0/P1/P2 级别:

```yaml
WHAT 分析:
  "新增" + "核心模块" → P0
  "修改" + "API" → P0
  "重构" + "无功能变更" → P2

WHY 分析:
  包含需求编号(如PRD-xxx) → P0
  包含"架构决策" → P0
  包含"优化" → P1

HOW 分析:
  涉及数据库schema → P0
  涉及API端点 → P0
  仅代码重构 → P2
```

### 自动识别受影响文档

**策略 1: 基于 related_files**

检查文档摘要中的 `related_files` 字段,匹配代码变更文件

**策略 2: 基于 HOW 分析**

解析 HOW 中提到的模块/文件,推断需要更新的文档

**策略 3: 基于传统规则**

降级到本文档定义的 P0/P1/P2 规则

### 降级策略

**场景 1: 非结构化 Commit**

- 基于 Git Diff 分析影响范围
- 使用本文档的传统规则判断优先级
- 提示用户补充变更意图

**场景 2: 混合 Commit**

- 聚合所有 commit 信息
- 优先使用结构化信息
- 传统 commit 作为补充

**详细说明**: 参见 [workflows/commit_guided_update.md](../workflows/commit_guided_update.md)

## 🎯 更新触发分级

### P0: 必须更新 (影响 AI 理解和开发效率)

**立即更新文档的情况**:

1. ✅ **新增核心功能模块**

   - 示例: 新增支付模块、用户系统等
   - 影响: AI 需要理解新模块的职责和接口

2. ✅ **架构重大变更**

   - 示例: 引入新的设计模式(MVC→MVVM)
   - 影响: 整体架构理解变化

3. ✅ **数据库 schema 变更**

   - 示例: 新增表、修改字段、改变关系
   - 影响: 数据模型理解变化

4. ✅ **API 接口重大变更**

   - 示例: 新增/删除端点、参数变化、响应格式变化
   - 影响: API 调用方式变化

5. ✅ **开发规范变更**
   - 示例: 状态管理方案改变(Vuex→Pinia)
   - 影响: 编码方式变化

6. ✅ **共享知识库重大更新** ⭐ (V3.0 新增)
   - 示例: 团队更新了核心架构模式或安全规范
   - 影响: 跨项目的一致性需要同步

### P1: 建议更新 (有助于保持文档准确性)

**建议更新文档的情况**:

1. ✅ **修复影响理解的重大 Bug**

   - 示例: 修复了架构设计缺陷
   - 影响: 对系统理解更准确

2. ✅ **新增重要配置项**

   - 示例: 新增环境变量、配置参数
   - 影响: 部署和配置方式变化

3. ✅ **第三方依赖大版本升级**

   - 示例: Vue 2→Vue 3, React 16→React 18
   - 影响: API 使用方式可能变化

4. ✅ **新增重要的最佳实践**
   - 示例: 新的错误处理模式
   - 影响: 代码质量提升

5. ✅ **新增本地知识条目** ⭐ (V3.0 新增)
   - 示例: 在 `dev_docs/knowledge/` 下新增了针对本项目的解决方案
   - 影响: 提升 AI 处理同类问题的效率

### P2: 可选更新 (不影响理解但可记录)

**可选更新的情况**:

- 小功能优化
- 代码重构(无功能变更)
- 文档错别字修正
- 性能优化(不改变接口)
- **删除过时的本地知识条目** ⭐ (V3.0 新增)

## 🔄 特殊场景更新指南

### 重构场景

**场景**: 代码重构但功能不变

**更新策略**:

- 如果 API/接口不变 → P2,可选更新
- 如果代码组织方式变化 → P1,建议更新主文档的目录结构章节
- 如果设计模式变化 → P0,必须更新架构文档

### 依赖升级场景

**场景**: 第三方依赖版本升级

**更新策略**:

- 小版本升级(如 1.2.3→1.2.4) → P2
- 中版本升级(如 1.2→1.3,API 兼容) → P1,更新版本号
- 大版本升级(如 1.x→2.x,breaking changes) → P0,全面更新相关文档

### 多模块项目场景

**场景**: Monorepo 或微服务架构

**更新策略**:

- 某个 package/service 变更 → 只更新该模块相关文档
- 共享库变更 → 更新所有依赖该库的文档
- 架构级别变更 → 更新 architecture_overview.md 及所有相关文档

## 🔄 更新方式

### 小范围更新

**适用场景**: P1 级别的变更,影响 1-2 个子文档

**操作步骤**:

1. 仅更新相关的子文档
2. 在子文档开头注明"最后更新"时间
3. 在主文档的更新记录中添加一条

**示例**:

```markdown
# API 层文档

> **最后更新**: 2025-11-27  
> **更新内容**: 新增支付接口说明

...
```

### 大范围更新

**适用场景**: P0 级别的变更,影响多个文档或架构

**操作步骤**:

1. 重新运行框架生成流程
2. AI 会检测已有文档
3. 增量更新变更的部分
4. 生成更新报告

**命令**:

```
告诉AI: "项目有重大更新,请更新AI文档"
并提供变更说明
```

## 💡 最佳实践

### 定期 review

**建议频率**:

- 小项目: 每月 review 一次
- 中大项目: 每 2 周 review 一次
- 重大迭代后: 立即 review

### 更新记录

在`AI_Coding_Context.md`中维护更新记录:

```markdown
## 📝 更新记录

| 日期       | 更新内容           | 影响范围                               | 更新人 |
| ---------- | ------------------ | -------------------------------------- | ------ |
| 2025-11-27 | 新增支付模块       | api_layer.md, architecture_overview.md | 张三   |
| 2025-11-20 | 数据库 schema 变更 | database_schema.md                     | 李四   |
```

### 团队协作

**多人项目**:

1. 指定文档维护负责人
2. 重大变更时通知负责人
3. 定期 review 会议讨论文档更新

## ❓ 常见问题

**Q: 如何判断是 P0 还是 P1?**  
A: 问自己:"如果 AI 不知道这个变更,会导致什么?"

- 会生成错误代码 → P0
- 会生成过时但不影响功能的代码 → P1
- 几乎无影响 → P2

**Q: 增量更新是什么意思?**  
A: AI 会:

1. 读取现有文档
2. 识别变更部分
3. 只更新变更的章节
4. 保留未变更的内容

**Q: 更新文档需要多久?**  
A:

- 小范围更新: 5-10 分钟
- 大范围更新: 20-30 分钟
- 完整重新生成: 与首次生成时间相同
